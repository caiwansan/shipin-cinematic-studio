## 1. 支付通知竞争条件 — 双倍扣款风险

**来源**: 后端代码审计
**文件**: `backend/src/routes/payment.ts:430-510`
**描述**: `handleVipRechargeOrder` 和 `handleAgentRechargeOrder` 收到支付系统重试通知时，状态检查 `if (order.status === 'paid') return` 未在 `prisma.$transaction` 内。并发重复通知可能都通过检查，导致积分/会员双重激活。
**建议**: 使用原子性 update（`where: { id, status: 'pending' }`）替代"先读后写"模式。
**影响**: 💰 用户积分可能被加两次，会员等级被双重激活

## 2. `process.env` API Key 污染 — 跨用户 Key 泄露

**来源**: 后端代码审计
**文件**: `backend/src/model-adapters/registry.ts:122-130`, `backend/src/config/env.ts:36-46`
**描述**: 注册表在调用前将用户 `runtime.apiKey` 写入 `process.env[provider.toUpperCase() + '_API_KEY']`，高并发下用户A的Key写入后，用户B的Key覆盖，然后A的finally中delete——B的Key永远丢失。同时 `env.ts:36-46` 无条件将所有配置值（即使空字符串）写回 `process.env`，空字符串被下游当作"已配置"。
**建议**: 废弃 process.env 写入模式，所有 provider 必须接收显式 apiKey 参数。
**影响**: 🔑 用户B的AI调用可能使用用户A的API Key或无Key失败

## 3. 积分扣减非原子性 — 积分透支漏洞

**来源**: 后端代码审计
**文件**: `backend/src/routes/user-center.ts:49-62`
**描述**: 先 `findUnique` 读余额、再 `update({ credits: { decrement: amount } })`，两个操作之间无事务。并发请求可绕过余额检查，扣到负数。
**建议**: 改为 `update({ where: { userId, credits: { gte: amount } }, data: { credits: { decrement: amount } } })` + 检查结果是否为 null
**影响**: 💳 用户可并发消耗比实际余额更多的积分

## 4. admin-storage-config.ts 完全无认证

**来源**: 架构审计
**文件**: `backend/src/routes/admin-storage-config.ts`

**建议**: 添加 `preHandler: [requireAdmin]`

## 5. `project.service.ts` findById 越权

**来源**: 架构审计
**文件**: `backend/src/services/project.service.ts` (findById)

**影响**: 👀 越权查看其他用户的项目内容

## 6. 内存缓存无限增长 — OOM 风险

**来源**: 后端代码审计 + 性能审计
**文件**: `backend/src/routes/auth.ts:30` (loginAttempts)、`backend/src/services/gateway-guard.ts:30` (userCallCounts/projectConcurrency)
**描述**: 三个内存 Map 无容量上限和自动清理机制。长期运行积累数百万条过期记录，最终 OOM。
**建议**: 
- loginAttempts: 实现定期清理（qq-oauth.ts 已有范例）
- gatewayGuard: 使用 Map + setInterval 清理策略
- 或统一迁移到 Redis（推荐）
**影响**: 🧠 服务运行数天后内存耗尽

## 7. `AbortSignal.timeout(120000)` 未清理 — 内存泄漏

**来源**: 后端代码审计 + 性能审计
**文件**: 所有 model-adapter 文件（aliyun-llm/openai-compat/dalle/siliconflow/siliconflow-tts/volcengine-video）
**描述**: 所有适配器使用 `AbortSignal.timeout(120000)` 创建超时控制器，请求完成后未销毁。Node.js 不会自动清理已创建的 AbortSignal。
**建议**: 使用 `AbortController` + `clearTimeout()` 显式控制生命周期
**影响**: 🧠 高并发 AI 调用场景下内存线性增长

## 8. Rate limiter 并发访问无锁 — 限速绕过

**来源**: 后端代码审计
**文件**: `backend/src/routes/auth.ts:168-174` (loginAttempts)、`backend/src/services/gateway-guard.ts:35-42` (userCallCounts)
**描述**: 内存 Map 计数在并发请求下存在竞争条件。`entry.count++` 非原子操作，多个请求同时通过检查。
**建议**: 生产环境使用 Redis INCR+EXPIRE，或使用 atomic 操作
**影响**: 🏃 用户可在1分钟内超过设定的20次限制

## 9. `execution-images.ts` HTTP 下载协议选择器 SSRF 绕过
