【P0】.env 文件包含明文凭据
──────────────────────────────────────────
严重程度：🔴 高
文件：.env / .env.bak
描述：生产环境密钥全部以明文写在 .env 和 .env.bak 中，包括：
  - 阿里云 DashScope: sk-fe9bfcb6ce4a45c6b40ccd25381c8617
  - 火山引擎: e7451bd2-bb62-4a53-a4a7-c0fb1ceb931f
  - DeepSeek: sk-1bea5ef7075948d1926a66fd5c0d526d
  - MinIO: AccessKey/SecretKey
  - PostgreSQL: postgres:postgres 明文密码
  - CRYPTO_ENCRYPTION_KEY 硬编码
影响：数据库、对象存储、AI 模型服务、短信服务全部可被攻破。
建议：立即轮换所有密钥；删除 .env.bak；使用环境变量注入。

【P0】ApiKey 表存在明文存储漏洞
──────────────────────────────────────────
严重程度：🔴 高
文件：routes/admin-api-keys.ts
描述：/api/admin/api-keys 的 POST/PUT 直接将用户输入的 keyValue 以明文存入
      ApiKey 表。而另一套路由 /api/admin/apikeys（admin-models-v2.ts）使用了
      AES-256-CBC 加密存储，存在两套重叠逻辑，一套明文一套加密。
影响：数据库泄露 = 所有第三方 AI 服务密钥泄露，直接经济损失+封禁风险。
建议：删除 admin-api-keys.ts 的明文实现，统一走加密路径。

【P1】CORS 配置为 origin: true（允许所有来源）
──────────────────────────────────────────
严重程度：🔴 高
文件：src/plugins/cors.ts
描述：origin: true 允许任何域名跨域访问 API，配合 JWT 无状态认证，
      任何第三方站点可构造 CSRF 攻击。
影响：所有 API 端点面临 CSRF 攻击风险。
建议：改为白名单配置，生产环境仅允许 aigc.fushtn.com。

【P1】OAuth 回调页面 XSS 风险
──────────────────────────────────────────
严重程度：🔴 高
文件：routes/wechat-oauth.ts, routes/qq-oauth.ts
描述：JWT token 以字符串拼接方式写入 HTML script 块：
      `"try { document.cookie = 'auth_token=" + token + "; …'; } catch(e){}"`
      如果 token 含引号/反斜杠，可导致 XSS 注入。
影响：OAuth 回调页面的 token 可被窃取。
建议：使用 JSON.stringify(token) 和 Set-Cookie header 替代拼接。

【P1】voice.ts 使用加密密文作为 API Key 调用第三方
──────────────────────────────────────────
严重程度：🔴 高
文件：src/routes/voice.ts:250
描述：saveUnified.ts 使用 AES-256-GCM 加密 API Key 存入 UserModelConfigV2，
      但 voice.ts:250 直接读取密文作为 volcApiKey 传给火山引擎 TTS API，
      未调用 decryptKey() 解密。api-keys.ts 返回给前端的也是密文字符串。
影响：所有 TTS/Image/Video 的 AI API 调用传入密文而认证失败（401/403），
      导致「无法创建音色」等用户反馈的根本原因。
建议：在 voice.ts 中 userCfg.ttsApiKey 后调用 decryptKey() 解密。

【P1】管理后台仅前端校验 token，后端的 admin 路由守卫被跳过
──────────────────────────────────────────
严重程度：🔴 高
文件：frontend/middleware/auth.ts, pages/admin/*
描述：middleware/auth.ts 显式跳过 admin 路径的认证检查。admin 页面的 API 
      调用失败后不会触发登出重定向，而是 fallback 到 mock 数据或显示错误。
      管理员 token 过期后页面仍可访问框架骨架。
影响：攻击者可绕过前台守卫直接访问管理页面 URL。
建议：admin 路由应调用 /api/admin/verify 验证，layout 加入 onMounted 检查。

【P1】CSP/X-Frame-Options/HSTS 安全头部全部缺失
──────────────────────────────────────────
严重程度：🔴 高
文件：frontend/nuxt.config.ts
描述：完全未配置 Content-Security-Policy、X-Content-Type-Options、
      X-Frame-Options、Strict-Transport-Security 等安全头部。
影响：XSS 无防御、站点可被嵌入 iframe 做点击劫持、可降级攻击。
建议：添加 nitro routeRules 配置完整安全头部。

【P1】管理后台明文显示/可编辑云密钥
──────────────────────────────────────────
严重程度：🔴 高
文件：pages/admin/aigc/*.vue（sms.vue, wechat.vue, qq.vue, payment.vue, models.vue, cos.vue）
描述：腾讯云 SecretId/SecretKey、微信支付密钥、所有 AI 提供商 API Key、
      MinIO 密钥等均在前端明文显示且可直接修改。
影响：管理员账号泄露 = 所有云服务凭证被盗，直接经济损失。
建议：密钥显示遮盖（****），修改走独立更新接口且不返回完整密钥。

【P1】localStorage + Cookie 双重存储 auth_token（可被 XSS 窃取）
──────────────────────────────────────────
严重程度：🔴 高
文件：frontend/studio-v2/stores/useStudioStore.ts, pages/community/post/[id].vue
      多处组件直接调用 localStorage.getItem('auth_token')
描述：Cookie 未设 HttpOnly 标记，任何 XSS 可读取 document.cookie。
      多处代码绕过 token-cache.ts 的内存缓存直接读 localStorage。
影响：XSS 注入后攻击者可窃取用户身份。
建议：前端所有 token 读取收敛到 token-cache.ts；关闭前端写 Cookie。

【P1】v-html 渲染社区帖子内容，sanitizeHtml 可绕过
──────────────────────────────────────────
严重程度：🔴 高
文件：pages/community/post/[id].vue:63
描述：使用手写正则 sanitizeHtml() 清洗用户内容后 v-html 渲染。
      正则绕过多：换行绕 onclick 过滤、大小写绕过、SVG 属性注入等。
影响：社区帖子可注入 XSS，管理员最先中招。
建议：改用 DOMPurify 替代手写正则，后端存储前也做净化。

【P2】OAuth 新用户创建时使用 randomUUID 作为密码
──────────────────────────────────────────
严重程度：🔴 高
文件：routes/wechat-oauth.ts, routes/qq-oauth.ts
描述：OAuth 新用户密码设置为 randomUUID().slice(0,16)，用户无法修改密码
      （无邮箱/手机绑定），且未 bcrypt 哈希。
影响：OAuth 账户无法正常管理密码，密码哈希字段存的可能是明文。
建议：OAuth 用户设 flag 标记为 OAuth-only，提供手机号绑定流程。

【P2】OAuth state 参数未校验（CSRF 缺失）
──────────────────────────────────────────
严重程度：🟡 中
文件：routes/wechat-oauth.ts, routes/qq-oauth.ts
描述：生成随机 state 后未在校验回调中验证 state 匹配。
影响：攻击者可构造 OAuth 回调 URL 诱导用户绑定攻击者账号。
建议：将 state 与临时 token 关联存储，callback 时校验。

【P2】SMS 验证码接口在日限溢出时返回明文 debugCode
──────────────────────────────────────────
严重程度：🟡 中
文件：routes/sms-auth.ts
描述：腾讯云短信日达上限时降级返回 { debugCode: code }，6 位验证码明文返回。
影响：生产环境泄露验证码。
建议：生产环境移除 debugCode 返回。

【P2】用户信息查询接口无需认证（user-by-email）
──────────────────────────────────────────
严重程度：🟡 中
文件：routes/auth.ts（/api/auth/user-by-email）
描述：通过邮箱查询用户信息，返回 memberTier、phone、agentStatus 等敏感字段。
影响：攻击者可枚举邮箱获取用户 VIP 等级、代理状态。
建议：添加 IP 限速，限制返回字段。

五、高并发与数据库连接池
================================================================================

【P0】数据库连接池严重不足（connection_limit=5 vs 6 PM2 实例）
──────────────────────────────────────────
严重程度：🔴 高
文件：.env （DATABASE_URL connection_limit=5）
描述：PM2 6 个实例 × 每个实例 8 个 PrismaClient（分散在各文件 new 的）
      = 至少 48 个连接需求，但 PostgreSQL 端限定了全局 connection_limit=5。
      且 Prisma 的 connection_limit 是 PostgreSQL 全局限制，不是每进程独立配额。
      当连接耗尽时 pool_timeout=30s 后请求超时，产生 "Too many clients" 级联故障。
影响：用户并发 > 5 时数据库连接被耗尽，整个 API 层不可用（503/502）。
建议：1) 废弃多 PrismaClient 实例，仅用 utils/index.ts 的单例（最优先）；
      2) 增大 connection_limit 到 20~50；
      3) 降低 PM2 实例数到 2~3。

【P1】Worker 并发 concurrency=10 会加剧连接竞争
──────────────────────────────────────────
严重程度：🔴 高
文件：queue/queue-manager.ts
描述：createWorkerPool 设置 concurrency=10，每个 worker 任务可能多次访问 DB，
      在 connection_limit=5 的情况下 10 个 worker 瞬间耗尽所有连接。
影响：worker 任务失败 → 重试 → 进一步恶化，形成雪崩。
建议：concurrency 降低到 3~5 并配合连接池扩容。

【P1】大文件上传/图片 base64 内存泄漏风险
──────────────────────────────────────────
严重程度：🔴 高
文件：frontend/AdvertisementWorkspace.vue（FileReader.readAsDataURL）
      backend/src/queue/worker-runtime.ts（Buffer.concat）
描述：前端 base64 编码文件膨胀约 33%，50MB 视频可吃掉 ~70MB 浏览器内存。
      后端 downloadImageLocal 用 Buffer.concat(chunks) 全内存缓冲。
      多段图片 + 大文件并发时存在 OOM 风险。
建议：前端限制上传大小，大文件使用 URL.createObjectURL() 替代 base64；
      后端改用 stream pipe 到文件。

【P1】任务重复执行缺少幂等性保证
──────────────────────────────────────────
严重程度：🔴 高
文件：queue/worker-runtime.ts, queue/queue-manager.ts
描述：persistImageResult 使用 create 而非 upsert，任务重试/超时重试时
      会重复插入 characterImage/sceneImage 记录。enqueueTask 中 jobId 
      可不传（undefined），丢失 BullMQ 去重能力。
影响：后端图片记录重复，前端渲染多条相同图片。
建议：persistImageResult 改为 upsert；enqueueTask 强制生成 taskId。

【P2】PM2 多进程写本地文件冲突
─────────────────────────────────────────
严重程度：🟡 中
文件：worker-runtime.ts, queue-manager.ts
描述：多进程同时 writeFileSync 到 public/uploads/，虽用 Date.now()+random 
      防冲突，但临时文件 /tmp/ 多进程混用有名冲突风险。
      IP 负载均衡下上传到 Node A 的文件从 Node B 访问不到。
建议：使用共享存储（COS/OSS）替代本地文件系统。

【P2】execution-images.ts N+1 循环 + 大事务
──────────────────────────────────────────
严重程度：🟡 中
文件：routes/execution-images.ts
描述：逐条 updateMany 循环 + 50+ 条 upsert 包在单个 $transaction 中。
      嵌套事务（643/658/673 行 3 个顺序事务），长时间持有连接。
影响：连接被长期占用，其他请求饿死。
建议：批量 upsert 拆为每 20~30 条分批提交，循环合入 where in 条件。

【P2】8 张表缺少 projectId 外键索引

八、工作流优化建议
──────────────────────────────────────────

【P2】Agent 生成流水线可大幅并行化
──────────────────────────────────────────
严重程度：🟡 中
文件：agents/aigc-orchestrator.ts
描述：当前严格 2 阶段串行（Phase 0→Phase 1→Phase 2），实际上：
  - 声音设计只依赖角色名，不依赖角色定妆和场景图
  - 道具设计只依赖角色和场景的概念，不依赖完整定妆
  8 个 Agent 串行执行总耗时 30s+。
优化建议：
  Phase 0: 剧情总指挥（必须最先）
  Phase 1（并行）：角色、场景
  Phase 2（并行）：定妆(依赖角色)、声音(依赖角色)、镜头(依赖场景)
  Phase 3（并行）：画面(依赖定妆+场景)、道具(依赖角色+场景)
  使用 DAG 调度替代硬编码阶段。

【P2】图片→视频→音频 依赖链可并行
──────────────────────────────────────────
严重程度：🟡 中
描述：TTS 只依赖剧本和角色音色，可在角色定妆完成后立即并行启动，
      与分镜图生成同时进行。视频段落也支持并发生成。
优化建议：TTS 与分镜图生成并行，视频段落用 Promise.all 并发提交。

【P2】帧序列引擎 FSE 并发可能打爆 API 配额
──────────────────────────────────────────
严重程度：🟡 中
文件：services/frame-sequence-engine.ts
描述：remainingShots 使用 Promise.all(concurrentTasks) 全部并发。
      对一段 5s 视频（粒度 0.5s=10帧），第 1~9 帧同时发起 image 生成。
      多段视频同时处理时可能 50+ 并发请求到同一 API Key。
影响：触发第三方 API（阿里百炼、硅基流动等）的并发限流（429）。
建议：增加并发控制 semaphore（如最大 3~5），或利用队列 concurrency 限制。
