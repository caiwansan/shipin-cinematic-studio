问题 S-01：PaymentSecret 表明文存储全部支付/认证密钥
──────────────────────────────────────────────────────────────────────────────
严重程度：  严重 ★★★★★
问题描述：  PaymentSecret 表以明文 JSON 格式存储全部第三方支付和认证凭据。
           该表 channel 字段包含 alipay、wechat、wechat_oauth、qq_oauth、
           sms_auth，config 字段为完整 JSON 对象，包含：
            - 支付宝：appId + 完整 RSA 私钥（PEM 格式）
            - 微信支付：appId + mchId + apiKey + apiV3Key + 完整 PEM 私钥
            - 微信 OAuth：appId + appSecret
            - QQ OAuth/OAuth：appId + appSecret
            - 短信：SecretId + SecretKey + SmsSdkAppId
           上述密钥既无加密也无遮挡。任何数据库泄露将导致攻击者可:
            - 直接用支付宝/微信私钥发起未授权支付请求
            - 伪造 OAuth 登录窃取用户身份
            - 滥用短信 API 发送垃圾信息产生巨额费用
影响：      数据库泄露 = 全部第三方密钥泄露 = 资金损失 + 用户身份伪造
位置：      backend/prisma/schema.prisma:1757-1768 (模型定义)
           数据库 PaymentSecret 表，5 条记录均明文（已通过 psql 验证）
           管理员前端接口：/api/admin/sms-auth/config 返回含 SecretId/SecretKey
修复建议：  1. 立即将所有 config 字段内容用 AES-256-GCM 加密存储
            2. 管理端读取时解密显示，日志中必须脱敏
            3. 新建解密专用的环境变量 CRYPTO_SECRET_KEY_PAYMENT（与现有加密密钥分离）
            4. 紧急轮换所有已在数据库中暴露的生产密钥
            5. REST API 返回配置时，SecretKey/privateKey/apiKey 必须完全脱敏

问题 S-02：.env 文件包含大量明文生产级 API Key
──────────────────────────────────────────────────────────────────────────────
严重程度：  严重 ★★★★★
问题描述：  backend/.env 文件中以明文存储了 10+ 个生产环境的 API Key 和密钥：
            - JWT_SECRET（用于签发所有用户 token）
            - ALIYUN_API_KEY（阿里云 AI 服务）
            - VOLCENGINE_API_KEY（火山引擎 AI 服务）
            - DEEPSEEK_API_KEY（DeepSeek AI 服务）
            - MINIO_ACCESS_KEY + MINIO_SECRET_KEY（对象存储）
            - CRYPTO_ENCRYPTION_KEY（数据库加密主密钥）
            虽然 .env 已被 .gitignore 排除，但服务器上任意能读取文件的用户
            或进程（如被 RCE 攻击）可直接获取所有 API Key。JWT_SECRET 的泄漏
            尤其严重——攻击者可伪造任意用户的 JWT token。
影响：      .env 文件读取 = 全部 API Key 和 JWT 密钥泄露 = 全量 API 冒充 + 数据泄露
位置：      backend/.env（服务器文件系统上，20+ 行密钥明文）
            backend/src/config/env.ts 中读取并设置到 process.env
修复建议：  1. 使用密钥管理服务（如 Vault, AWS Secrets Manager）替代 .env 文件
            2. 限制 .env 文件权限为 600（仅 owner 可读）
            3. 立即轮换所有在 .env 中暴露的 API Key
            4. JWT_SECRET 建议使用独立的密钥管理机制，定期轮换
            5. 添加文件完整性监控（如 AIDE / Tripwire）检测 .env 是否被读取

──────────────────────────────────────────────────────────────────────────────

              用户也可以通过返回的调试码完成验证。
            3. 日限达到时降级逻辑自动返回调试码（第97行 mock返回），
              攻击者可无限使用调试码穷举攻击。
影响：      返回调试码 = 短信验证码形同虚设 + 可被暴力破解
            缺少索引 = 性能问题 + 可能的时序攻击窗口
位置：      backend/src/routes/sms-auth.ts:92-98 (返回调试码)
            backend/src/routes/sms-auth.ts:116-117 (成功后返回调试码)
            数据库 SmsCode 表（无 phone 索引）
修复建议：  1. 立即在 SmsCode 表 phone 列上添加索引
            2. 删除所有返回 debugCode 的逻辑——线上环境绝不能泄露验证码
            3. 调试码机制应通过环境变量开关控制，且仅开发环境可用
            4. 增加 EmailCode 表的 email 列的索引（同样缺失）

问题 S-04：StorageConfig 表 accessKey 明文存储
──────────────────────────────────────────────────────────────────────────────
严重程度：  严重 ★★★★★
问题描述：  storage_configs 表的 accessKey 列以明文存储，secretKey 列虽然

            1. accessKey 完全未加密
            2. 解密回退逻辑（decryptKey 中的 catch）在解密失败时会返回原文，

              解密后密钥保存在内存中

            对象存储全量访问权限泄露
位置：      backend/prisma/schema.prisma:3361-3377 (accessKey 无 @encrypted 注释)
            backend/src/services/crypto.service.ts:33-36 (密钥来自 .env)
            backend/src/services/cos-service.ts:44-50 (解密回退逻辑)
修复建议：  1. accessKey 也应加密存储，与 secretKey 使用同一方案
            2. 移除 decryptKey 中解密失败返回明文的 catch 逻辑
            3. 存储加密密钥与管理加密密钥分离
            4. 内存中使用的解密密钥使用后及时置零

──────────────────────────────────────────────────────────────────────────────
严重程度：  严重 ★★★★★

            POST /api/auth/sms/login、POST /api/auth/sms/reset-password）
           均未设置任何图形验证码（CAPTCHA）或限速中间件（除了内存中的

           而且日限是20条/天的宽松限制，攻击者没必要穷举日限，
           因为 send 接口直接就返回了调试码。
影响：      短信验证码机制完全失效 → 任何知道手机号的人可登录任意账户
位置：      backend/src/routes/sms-auth.ts:74 (send 接口无 CAPTCHA)
            backend/src/routes/sms-auth.ts:128 (login 接口无 CAPTCHA)
            backend/src/routes/sms-auth.ts:191 (reset-password 接口无 CAPTCHA)
修复建议：  1. 所有短信接口添加图形验证码校验（复用现有的 captcha.ts）
            2. 添加全局短信发送频率限制中间件，基于 IP+手机号双因子
            3. 删除所有调试码返回逻辑
            4. 添加登录 IP 异常检测（同一 IP 短时间内多个手机号登录尝试）

问题 H-01：JWT 单设备登录 tokenVersion 机制的安全隐患
──────────────────────────────────────────────────────────────────────────────
严重程度：  高危 ★★★★☆
问题描述：  认证插件的单设备登录检查（tokenVersion 对比）尽管提供了基本的
           会话管理功能，但实现存在缺陷：
           1. 每次短信登录都增加了 tokenVersion，意味着每次登录都会使所有
              已有 token 失效——这对用户不友好且容易误判
           2. tokenVersion 增加后旧 token 立即失效，但攻击者如果截获了
              JWT token 可以在 tokenVersion 更新前完成操作
           3. 会话没有 refresh token 机制，所有 token 有效期 30 天
           4. 登出接口（/api/auth/logout）仅作通知，不实际失效 token
           5. 没有 token 黑名单机制
影响：      token 有效期过长（30天）+ 无黑名单 → token 泄露后影响期长
            单设备逻辑粗糙 → 用户正常使用受影响
位置：      backend/src/plugins/auth.ts:13-28 (tokenVersion 检查)
            backend/src/routes/auth.ts (login 接口的 tokenVersion 更新)
            backend/src/routes/sms-auth.ts:168 (登录时 tokenVersion +1)
修复建议：  1. 实现 refresh token 机制（短期 access token + 长期 refresh token）
            2. 维护 server-side token 黑名单（Redis 或数据库）
            3. 降低 access token 默认有效期至 1-2 小时
            4. logout 接口实际将 token 加入黑名单
            5. 或保留长有效期但增加登出/密码修改后版本号更新的逻辑

问题 H-02：Login 速率限制基于内存 Map，重启后重置
──────────────────────────────────────────────────────────────────────────────
严重程度：  高危 ★★★★☆
问题描述：  登录尝试频率限制（5次失败封禁15分钟）完全基于 Node.js 进程
           内的内存 Map（loginAttempts），这意味着：
           1. 服务器重启后限制完全清零
           2. 多进程部署时（PM2 cluster 模式），每个进程独立计数，
              攻击者可轮询各进程突破限制
           3. 分布式部署时完全无效
影响：      暴力破解防护仅在单进程单次运行期间有效，重启/扩展后失效
位置：      backend/src/routes/auth.ts:7-8 (内存 Map 定义)
            backend/src/routes/auth.ts:40-51 (限速逻辑)
修复建议：  1. 使用 Redis 存储登录失败计数，设置 TTL 自动过期
            2. 或使用现有的 @fastify/rate-limit 插件统一管理
            3. 添加 IP 级别的全局限速

问题 H-03：Token 同时存储在 localStorage 和 Cookie，且 Cookie 未设置 HttpOnly
──────────────────────────────────────────────────────────────────────────────
严重程度：  高危 ★★★★☆
问题描述：  前端 auth store 在登录后将 JWT token 同时存储到：
           1. localStorage（通过 token-cache.ts 的 setToken）
           2. document.cookie（仅设置 samesite=lax，未设置 HttpOnly/Secure）
            
           localStorage 中的 token 对所有 JavaScript 可读：
           - XSS 攻击可窃取 token（尽管代码注释称"内存闭包防御XSS"，
             但 localStorage 读取不需要闭包访问，直接 localStorage.getItem 即可）
           - Cookie 未设置 HttpOnly 意味着 JavaScript 同样可以读取
           
           另外 token-bridge.client.ts 将 token 操作挂载到 window.__token_cache
           上，任何第三方脚本都可以通过该全局对象获取 token。
影响：      XSS 攻击成功即可窃取用户 JWT token → 账户完全被盗
位置：      frontend/stores/auth.ts:62, 63, 66, 67 (写入 cookie)
            frontend/utils/token-cache.ts (localStorage 读写)
            frontend/plugins/token-bridge.client.ts:15-24 (暴露到 window)
修复建议：  1. 使用 HttpOnly、Secure、SameSite=Strict 的 Cookie 存储 token
            2. 或使用 BFF（Backend-for-Frontend）模式，前端只存短期 session
            3. 不要将 token-cache 暴露到 window 全局对象
            4. 移除调试用的 token-bridge 插件

问题 H-04：管理后台 API 认证不统一且存在绕过风险
──────────────────────────────────────────────────────────────────────────────
严重程度：  高危 ★★★★☆
问题描述：  admin-storage-config.ts 中的所有管理接口（GET/POST/DELETE）手动
           检查 Authorization header 前缀，而非使用统一的 fastify.authenticate
           装饰器或 requireAdmin 中间件。手动解析的代码可能遗漏边界情况：
           - 仅检查 headers.authorization 是否以 'Bearer ' 开头
           - 未验证 token 有效性，未检查用户角色
           - 验证过程可能被畸形 header 绕过
           
           同时，verifyToken() 函数在 admin-auth.ts 中定义，但 admin-storage-config
           根本没调用——它只检查有没有 Bearer 前缀，不校验 token 是否有效。
影响：      管理后台存储配置接口存在严重的认证绕过风险
位置：      backend/src/routes/admin-storage-config.ts:30-32 (GET 认证)
            backend/src/routes/admin-storage-config.ts:45-47 (POST 认证)
            backend/src/routes/admin-storage-config.ts:88 (DELETE 认证)
            backend/src/routes/admin-storage-config.ts:104 (default 认证)
修复建议：  1. 统一使用 fastify.authenticate 装饰器
            2. 添加 requireAdmin 中间件检查管理员角色
            3. 所有管理接口应校验 token 及角色权限

问题 H-05：QQ OAuth callback 中 access_token 直接暴露在 URL 中
──────────────────────────────────────────────────────────────────────────────
严重程度：  高危 ★★★★☆
问题描述：  QQ OAuth 回调流程存在严重安全问题：
           1. access_token 在 Step 1 中通过 URL query 参数传输（code 换 token），
              攻击者可通过中间人攻击或浏览器历史记录获取 access_token
           2. access_token 后续被直接拼接到 URL query 中调用 me API 和
              get_user_info API（https://graph.qq.com/...?access_token=...）
           3. 未使用 PKCE 扩展（QQ OAuth 2.0 也不支持），但 access_token 在
              服务端调试日志中被完整打印（console.error）
           4. QQ appSecret 已存储在 PaymentSecret 表中明文可读
影响：      access_token 泄露 → 攻击者可获取用户 QQ 身份信息
           日志暴露 → 运维人员可获取 access_token
位置：      backend/src/routes/qq-oauth.ts:125-126 (access_token 拼入 URL)
            backend/src/routes/qq-oauth.ts:139 (me API 含 access_token)
            backend/src/routes/qq-oauth.ts:150-152 (get_user_info 含 access_token)
修复建议：  1. 不要在日志中打印 access_token
            2. 服务端处理完成后立即丢弃 access_token
            3. 考虑使用 state 参数绑定机制加强 CSRF 防护

问题 M-01：APIKey 表存储用户 API Key 时仅统一加密，缺少用户级隔离
──────────────────────────────────────────────────────────────────────────────
严重程度：  中危 ★★★☆☆
问题描述：  ApiKey 表是一个全局表，存储所有 provider 的 API Key。
           这些 Key 是由平台管理员配置的全局 API Key（非用户私有）。
           而 UserModelConfigV2 表存储用户自有的 API Key（llmApiKey,
           imageApiKey 等）。
           
           问题在于：UserModelConfigV2 的 API Key 字段类型是 String?，
           在 Prisma schema 中没有注释说明是否加密。根据代码审查，
           在 with-user-key.ts 中解密时虽然调用了 crypto.service，但
           如果数据库中存储的是未加密的原始 key（fallback 场景），则
           可能返回明文。同时，ApiKey 表中的 keyValue 字段是 String 类型，
           在加载时先尝试解密，失败则当成明文直接使用（index.ts:89-92行）。
影响：      部分 API Key 可能以明文形式存储在数据库中
位置：      backend/prisma/schema.prisma:1488-1495 (ApiKey 表)
            backend/src/index.ts:89-92 (解密失败 fallback 为明文)
            backend/prisma/schema.prisma:1500-1533 (UserModelConfigV2)
修复建议：  1. 添加数据库层面的字段注释标明加密状态
            2. 移除解密失败 fallback 明文逻辑，应记录错误并拒绝使用
            3. 统一所有 API Key 的加密方案，增加数据迁移脚本加密旧数据

──────────────────────────────────────────────────────────────────────────────

问题 M-03：CORS 配置允许凭据 + 反射来源
──────────────────────────────────────────────────────────────────────────────
严重程度：  中危 ★★★☆☆
问题描述：  CORS 插件配置了 credentials: true，且 origin 来源是
           环境变量 CORS_ORIGIN（默认值 https://aigc.fushtn.com）。
           但某些情况下如果 CORS_ORIGIN 未设置，使用默认值问题不大。
           
           更大的风险是：后端没有为所有 API 添加统一的 CSRF 防护机制。
           虽然 CORS 限制了跨域请求，但结合 credentials: true 时，
           如果子域名被攻破或存在其他漏洞，攻击者可构造跨站请求。
影响：      credentials: true 的 CORS 配置 + 无 CSRF 防护 → CSRF 风险
位置：      backend/src/plugins/cors.ts:6-9
            backend/.env 中 CORS_ORIGIN=https://aigc.fushtn.com
修复建议：  1. 在状态变更类 API 添加 CSRF token 验证
            2. 考虑启用 SameSite=Strict Cookie 策略
            3. CORS 白名单应严格配置，避免使用通配符

问题 M-06：前端敏感信息泄漏（认证用户数据存储在 Cookie）
──────────────────────────────────────────────────────────────────────────────
严重程度：  中危 ★★★☆☆
问题描述：  前端 auth store 在登录后将用户对象序列化后写入 Cookie：
            document.cookie = `auth_user=${encodeURIComponent(JSON.stringify(this.user))}; path=/; max-age=86400; samesite=lax`
           该 Cookie 未设置 HttpOnly 和 Secure，用户敏感信息（id,

            frontend/stores/auth.ts:87 (auth_user cookie - phone login)
            frontend/stores/auth.ts:107 (auth_user cookie - fetchMe)
            frontend/stores/auth.ts:118-122 (auth_user cookie - restoreSession)
修复建议：  1. 不要将用户数据存储到 Cookie 中
            2. 用户数据保持 Pinia store 内存状态即可
            3. 必要的持久化使用 HttpOnly Cookie

问题 L-01：Content-Security-Policy 允许 'unsafe-inline' 和 'unsafe-eval'
──────────────────────────────────────────────────────────────────────────────
严重程度：  低危 ★★☆☆☆
问题描述：  nuxt.config.ts 中配置的 Content-Security-Policy：
           script-src 'self' 'unsafe-inline' 'unsafe-eval'
           允许了不安全的内联脚本和 eval 执行。虽然 Nuxt SPA 需要
           内联脚本，但 'unsafe-eval' 通常可以避免。
           前端依赖的 Vue 和 Three.js 等库在现代版本中不需要 eval。
影响：      XSS 攻击面增大——即使有 CSP 保护，unsafe-inline 允许攻击者
           注入任意内联脚本
位置：      frontend/nuxt.config.ts:35-36 (CSP 配置)
修复建议：  1. 尝试移除 'unsafe-eval'，使用 nonce 或 hash 策略替代
            2. 生成的 CSP 应通过报告模式（report-uri / report-to）先监控
            3. 考虑使用 strict-dynamic 策略

──────────────────────────────────────────────────────────────────────────────

安全评分：32 / 100 （非常危险）

评分明细：
  ├─ 数据库安全          20/100  — PaymentSecret 明文存储、SmsCode 无索引
  ├─ 认证安全            25/100  — 调试码机制完全绕过、JWT 过长、无 refresh
  ├─ API 安全            35/100  — 管理 API 认证不统一、无 CSRF、无输入校验
  ├─ 密钥管理            15/100  — .env 明文存储、加密密钥泄露、解密 fallback
  ├─ 前端安全            40/100  — localStorage + Cookie 存储、CSP 宽松
  └─ 基础设施安全        55/100  — 依赖管理不足、审计日志缺失

总体评级：★★★★★ (5/5 危险)
该应用当前处于极不安全状态。最严重的问题是：

1. PaymentSecret 表明文存储全部支付/认证密钥（包括支付宝私钥、微信 API 密钥）—— 
   这是灾难性的，一次数据库泄露将导致全部第三方服务密钥泄露，可直接造成资金损失。

2. 短信验证码系统在后端返回调试码，使短信验证完全形同虚设——任何知道手机号的人
   都可以通过调试码登录任意账户。

3. .env 文件包含大量明文生产 API Key，任意能读取服务器文件系统的进程即可获得全部
   第三方服务访问权限。

4. JWT token 同时存储在 localStorage 和 Cookie（无 HttpOnly），XSS 攻击可直接窃取。
   
建议立即采取行动：
  - 紧急处理：轮换所有在数据库中明文的密钥（支付密钥、API Key）
  - 紧急处理：删除短信接口返回调试码的逻辑
  - 紧急处理：加密 PaymentSecret 表的所有配置数据
  - 短期修复：移除代码中所有返回敏感信息的逻辑
  - 短期修复：实现统一的认证中间件、输入校验、审计日志
  - 长期规划：引入 Vault/Secrets Manager、密钥轮换机制、安全开发生命周期
