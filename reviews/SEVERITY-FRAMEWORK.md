# FCV-1 Severity Framework（问题严重度分级）

> **版本**: v1.0 | **用途**: 确定哪些反馈应该修、哪些不应该修

---

## 分级标准

| Level | 定义 | 示例 | 是否阻塞 Phase D 通过 |
|---|---|---|---|
| **S0** | 无法完成 Journey | 用户找不到入口 / Mission 无法创建 / 验证不触发 / 流程断裂 | ✅ YES — 必须修复后才能继续 FCV |
| **S1** | 能完成但有大量困惑 | 用户停留在某页面超过 3 分钟 / 回退 2 次以上 / 需要主持人心理解释才能继续 | ✅ YES — 必须在 Phase D 结束前修复 |
| **S2** | 能完成但体验差 | 用户完成了任务但表达了 frustration / 理解了对但慢 | ⏳ Sprint 修复 |
| **S3** | 建议或偏好 | "如果有深色模式就好了" / "字体能不能大一点" | 📥 Backlog — 暂不处理 |

---

## 严重度判定流程

```
Observation
  ↓
这是阻塞 Journey 吗？           → YES → S0
  ↓ NO
这是导致用户困惑超过 30 秒吗？  → YES → S1
  ↓ NO
这是让用户感到不爽吗？          → YES → S2
  ↓ NO
这是用户建议/偏好？             → YES → S3
```

---

## 关于 S0 和 S1 的特别规则

- **S0 问题**：FCV-1 期间一旦发现，立即记录。如果达到 3 个不同用户触发相同的 S0 → FCV-1 暂停，优先修复。
- **S1 问题**：FCV-1 结束后汇总。如果修复后能显著提升"无帮助完成率"→ 列入修复 Sprint。

---

## 客户 Truth Review 时的 Severity 使用方式

只看 S0 + S1：
```
如果 S0 存在 → Journey 有断裂 → 不能进入 Phase E
如果只有 S2/S3 → Journey 成立 → 可以进入 Phase E
```
