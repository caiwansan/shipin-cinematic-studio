# ADR-004: Repository + ORM Adapter 模式

- **状态**: Accepted
- **日期**: 2026-07-17
- **提出者**: XiongDa (架构师)

## 背景

架构审计发现数据访问层存在严重的模式违规：

- **13 个重复的 `mapPrisma` 函数**散布在 8 个 Repository 和 3 个 Service 中
- **Service 层直接 import prisma**，绕过 Repository 封装
- `BrandProfile`、`WebsiteSnapshot` 等模型直接在 Service 中使用 Prisma 查询
- 数据映射逻辑（prisma 记录 → 业务模型）分散在多个文件中，修改一个字段需要改 5-6 处
- 无法单元测试——所有测试都需要启动数据库

更根本的问题是：**数据访问层与 Prisma 紧耦合**，未来无法切换到 Drizzle 或其他 ORM。

## 决策

**采用 Repository 模式 + ORM Adapter 接口，Prisma 作为其中一种实现。**

```
Service Layer → Repository Interface → ORMAdapter → PrismaAdapter（当前默认）
                                                → DrizzleAdapter（未来备选）
                                                → KyselyAdapter（未来备选）
```

关键变更：
1. `BaseRepository` 不再直接引用 Prisma，改为引用 `ORMAdapter` 接口
2. 新增 `ORMAdapter` 接口定义（create/findById/findMany/update/softDelete 等）
3. `PrismaAdapter` 是 `ORMAdapter` 的一个实现——不是唯一实现
4. `mapPrisma` 重命名为 `mapToDomain`，语义更清晰

## 理由

1. **ORM 可替换**：Prisma 不是终局选择，Drizzle 更轻量、Kysely 类型更安全
2. **可测试性**：可以 mock ORMAdapter 进行单元测试，无需启动数据库
3. **集中数据变换**：mapToDomain 在 Repository 中，不再是散落在 Service 中的 mapPrisma
4. **统一错误处理**：数据库连接错误、超时、死锁在 Adapter 层统一处理

## 后果

### 正面
- 13 个 mapPrisma 合并到对应 Repository
- Service 层不再 import prisma
- 数据库单元测试成本降低
- ORM 切换时只需新写一个 Adapter 实现

### 负面
- 所有现有 Repository 需要修改构造函数——从 `new Repository(prisma)` 改为 `new Repository(adapter)`
- Service 中的 prisma 调用需要迁移到 Repository
- 前期的开发成本——因为当前 100% 使用 Prisma，ORM Adapter 的抽象短期内是纯开销
- 初始 Prisma 锁定是可接受的，因为切换 ORM 不是当前优先事项

## 替代方案

| 方案 | 拒绝原因 |
|------|---------|
| 保持现状（直接 Prisma） | 13 份重复 mapPrisma、Service 直接 import prisma——已造成维护噩梦 |
| 只加 Repository，不加 ORM Adapter | Repository 仍然直接依赖 Prisma，未来无法切换 ORM |
| 使用 Prisma 的中间件机制 | Prisma middleware 无法解决模型映射问题，且只能做简单拦截 |
