# ADR-003: 能力层架构（Capability Layer Architecture）

- **状态**: Accepted
- **日期**: 2026-07-17
- **提出者**: XiongDa (架构师)

## 背景

审计发现 8/8 的 Agent 全部是 stub（桩实现），Workspace（如 GEO）在 Service 层直接调用 LLM Provider，没有统一的调用路由：

- Brand GEO 的 Service 硬编码了 Doubao 调用
- KMKI 的 Agent 通过不同的方式注册 Provider
- Provider 切换需要修改 Workspace 代码
- 没有 Provider 健康检查和自动降级

需要一种架构，让 Workspace 不关心底层使用哪个 Provider。

## 决策

**采用四层能力模型：Provider → Model → Capability → Workflow → Workspace**

```
Provider Layer  →  Model Layer  →  Capability Layer  →  Workflow  →  Workspace
(OpenAI,        (gpt-4,         (llm.generate,      (DAG 编排,     (UI +
 DeepSeek,       deepseek-v3,   image.generate,     Agent 调度)    Adapter)
 Qwen)           qwen-max)      tts.generate)
```

关键分层：
- **Provider 层**：具体的 AI 服务商适配器
- **Model 层**（新增）：Provider 提供的模型实例，是 Workspace 直接引用的层级
- **Capability 层**：能力注册、路由、调用分发、健康检查、降级
- **Workflow 层**：DAG 编排，Agent 调度
- **Workspace 层**：只调用 Capability，不关心 Provider/Model

## 理由

1. **Provider 透明**：Workspace 不关心用哪个 Provider——从 Doubao 切换到 Qwen 不需要改 Workspace 代码
2. **Model 级路由**：不同模型版本可以有不同的系统提示词和参数，模型映射由平台管理
3. **自动降级**：Primary Provider 不可用时自动切换到 Fallback，Workspace 无感知
4. **能力发现**：Workspace 可以通过 `listCapabilities()` 发现可用 Agent 和能力

## 后果

### 正面
- Provider 切换配置化，修改配置文件即可
- Agent stub 有了明确的实现目标——实现 `AgentRegistration` 接口
- 健康检查 + 自动降级 + 重试统一实现

### 负面
- 增加了一层抽象（Model 层），调用链路变长
- 8 个 stub Agent 需要全部重写为真实的 Agent 实现
- Covalent（调用链路追踪）需要适配新的分层

## 替代方案

| 方案 | 拒绝原因 |
|------|---------|
| Workspace 直接调用 Provider | 紧耦合，Provider 切换需改代码，已证明不可行 |
| 两层模型（Provider → Capability） | 缺少 Model 抽象，无法实现"同模型不同 Provider"的路由 |
| Capability 层实现在 Workspace 中 | 违反 Platform First 原则，能力不共享 |
