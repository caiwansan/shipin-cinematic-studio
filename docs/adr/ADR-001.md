# ADR-001: 单一运行时（Single Runtime）

- **状态**: Accepted
- **日期**: 2026-07-17
- **提出者**: XiongDa (架构师)

## 背景

昆仑镜 V3 及 V4 前期各 Workspace 拥有独立的运行时实现：

- **Video Workspace**：有自己的运行时上下文和管理逻辑
- **GEO Workspace**：存在 2 个独立的运行时——`geo.runtime.ts`（KMKI，~80 行）和 `useBrandGEORuntime.ts`（Brand，~280 行）
- **Novel Workspace**：有自己的运行时编排

这导致了一系列架构问题：
- 运行时逻辑重复（retry、timeout、状态管理等每个 Workspace 各自实现一遍）
- 执行行为不一致（A Workspace 和 B Workspace 的重试策略不同）
- 跨 Workspace 状态共享需要额外机制（甚至不可能）
- 新的 Workspace 需要从零构建运行时

## 决策

**采用单一 Platform Runtime，Workspace 通过 Adapter 模式消费 Runtime 能力。**

Platform 层提供四种运行时类型：
1. **ExecutionRuntime** — 单操作执行生命周期
2. **WorkflowRuntime** — DAG 编排与调度
3. **CapabilityRuntime** — Provider 路由与降级
4. **StateRuntime** — 状态管理

Workspace 不再拥有任何运行时实现，只通过 `WorkspaceAdapter` 接口与 Platform Runtime 交互。

## 理由

1. **消除重复**：Runtime 逻辑集中在 Platform 层一处，所有 Workspace 共享
2. **一致的生命周期管理**：所有被执行的操作遵循相同的 retry/timeout/cancel 策略
3. **跨 Workspace 状态共享**：StateRuntime 统一管理状态，GEO 事件可触发 Video 动作
4. **新 Workspace 零运行时投入**：新 Workspace 只需实现 Adapter 接口

## 后果

### 正面
- 运行时实现从 3+ 缩减到 1 套
- 执行行为可观测（统一 telemetry）
- 新 Workspace 开发效率提升

### 负面
- Workspace 失去执行逻辑的自主权（不能在 Adapter 中自定义 retry 策略）
- 两个 GEO Runtime 需要完全重写为 Adapter
- 平台 Runtime 本身成为单点故障（需高可用保障）

## 替代方案

| 方案 | 拒绝原因 |
|------|---------|
| 保持各自 Runtime | 重复代码和架构混乱，已证明不可持续 |
| 提供 Runtime Base Class 让 Workspace 继承 | 继承导致强耦合，违反接口隔离原则 |
| Micro-frontend 各自独立 | 运维成本高，跨 Workspace 协作困难 |
