# ADR-002: Workspace Adapter 模式

- **状态**: Accepted
- **日期**: 2026-07-17
- **提出者**: XiongDa (架构师)

## 背景

各 Workspace（GEO、Video、Novel、PPT）的业务逻辑和交互方式差异巨大——视频编辑和品牌分析显然不是同一回事。但在架构层面，它们共享相同的结构性模式：

- 都需要注册到平台
- 都需要处理业务 action
- 都需要在销毁时释放资源
- 都需要通过 SDK 与平台交互

面临的选择是：如何让千差万别的 Workspace 遵循统一的平台契约？

## 决策

**采用 Adapter 模式，通过 `WorkspaceAdapter` 接口契约实现 Workspace 与 Platform 的解耦。**

```typescript
export interface WorkspaceAdapter {
  readonly id: string
  register(ctx: WorkspaceContext): Promise<void>
  execute<TInput, TOutput>(action: string, input: TInput, ctx: WorkspaceContext): Promise<TOutput>
  dispose(): Promise<void>
}
```

每个 Workspace 必须实现且只能实现一个 `WorkspaceAdapter`。

## 理由

1. **松耦合**：Adapter 是一个接口，Workspace 的内部实现完全不可见
2. **接口契约强制**：所有 Workspace 必须实现 `register/execute/dispose`，没有"忘记实现"的可能
3. **可测试性**：Platform 可以 mock Adapter 进行集成测试，Workspace 可以 mock PlatformSDK 进行单元测试
4. **替换成本低**：如果一个 Workspace 需要全新实现，只需重新实现 Adapter

## 后果

### 正面
- Platform 不依赖具体 Workspace 实现
- 测试覆盖更容易（接口 mock）
- 新的 Workspace 类型可以快速接入

### 负面
- Adapter 实现必须全部符合同一接口——某些 Workspace 的业务入口不适合 `execute(action, input)` 模式
- GEO 的两个独立代码库（KMKI + Brand）需要合并为一个 Adapter，重构工作量较大
- Adapter 之外的业务逻辑（如组件、Service）仍然可能违规

## 替代方案

| 方案 | 拒绝原因 |
|------|---------|
| 基类继承 `BaseWorkspace` | 继承导致强耦合，公共方法修改影响所有子类，违反"组合优于继承"原则 |
| 无接口（Platform 直接调用 Workspace 模块） | 无法约束 Workspace 行为，需要运行时反射检测 |
| Plugin 热插拔 | 过于复杂，Workspace 不是插件——它们是平台的永久组成部分 |
