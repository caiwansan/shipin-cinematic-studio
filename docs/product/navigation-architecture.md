# GEO Navigation Architecture

> **将 Engine 导航重构为任务导航 —— 降低认知负担，完成"用户不需要理解内部架构"的产品承诺**
>
> 版本：v1.0
> 依据：First 15 Minutes Blueprint v1.0 · GEO PRODUCT WHITEPAPER V1 · Product Readiness Audit
> 冻结日期：2026-07-26

---

## 核心原则

### Principle 1：任务语言 > Engine 语言

用户不关心 Health Engine、Discovery Engine、Mission Engine。用户关心的是"我的品牌现在怎么样"、"接下来该做什么"、"做完了有什么效果"。

**一级导航用用户能理解的任务名称，而不是系统模块名称。**

| ❌ Engine 语言 | ✅ 任务语言 |
|---|---|
| Health / ADI | 开始优化 |
| Discovery / Mission | 执行建议 |
| Verification | 验证效果 |
| Publishing / Knowledge | 发布成果 |
| Dashboard / Growth | 持续增长 |

**为什么？** Audit (Cognitive Load ⭐2/5) 显示用户需要理解引擎链才能有效使用产品。白皮书第三章明确要求"GEO 必须以普通商业用户能够理解和操作为原则，不得要求用户理解底层 AI 技术。"

### Principle 2：三秒原则

进入任何页面，用户三秒内知道：
1. **我在哪** — 导航高亮 + 面包屑
2. **我该做什么** — 每页只有一个 Primary Goal
3. **做完得到什么** — Outcome 可预期、可感知

Blueprint 的"3-second Check"是每个页面的硬性验收标准。

### Principle 3：Engine 名称降级

Discovery、Knowledge、Mission、Verification Engine 等名称**只出现在页面二级标题或功能入口中**，不作为一级导航。

例如：用户在"执行建议"页面看到一个 Mission 卡片，标题是"添加品牌描述"，副标题小字写着"由 AI 品牌引擎自动生成"——但用户不需要理解这个引擎是什么。

### Principle 4：每个页面只有一个 Primary Goal

禁止一个页面同时承担"查看健康"+"创建任务"+"发布内容"三个目标。如果需要多目标，拆分到不同 Tab 或不同页面。

### 1.2 导航表

| 一级（任务语言） | 二级（包含页面） | 用户任务 | 什么时候高亮 |
|---|---|---|---|
| **开始优化** | Health / Discovery | "看看品牌在 AI 眼中怎么样" | 新品牌创建后、无扫描结果时 |
| **执行建议** | Recommendations / Mission | "按 AI 建议优化品牌" | Health 页面展示后、有推荐项时 |
| **验证效果** | Verification | "看看优化有没有效果" | 执行完优化后自动跳转 |
| **发布成果** | Publishing / Knowledge | "让品牌知识被更多渠道看到" | 完成至少 1 项优化后 |
| **持续增长** | Dashboard / Growth | "追踪品牌成长趋势" | 任何剩余时间可见，首次旅程第 12-15 分钟 |

### 1.3 全局性入口

| 入口 | 位置 | 内容 | 始终可见 |
|---|---|---|---|
| 品牌选择器 | 导航栏左上角 | 当前品牌名 + 下拉切换 | ✅ 始终可见（有品牌时） |
| 设置 | 导航栏右上角 | 用户信息、通知偏好、账号设置 | ✅ |
| 帮助/引导 | 设置旁边 | 新手引导、文档入口、快捷键 | ✅ |
| 品牌创建入口 | 品牌选择器底部 | 添加新品牌（"+ 添加品牌"） | ✅ |

## 2. 每个导航项的详细规格

### 2.1 开始优化

| 规格 | 值 |
|---|---|
| **用户语言名称** | 开始优化 |
| **包含页面** | Health 页面、Discovery（扫描过程） |
| **用户什么时候看到它** | 始终可见，第一个 tab；无品牌时仍显示但内容为空引导 |
| **何时高亮** | 首次旅程 Phase 1-2（0-6 分钟），或当前品牌无扫描结果时 |
| **何时不可用/灰度** | 无品牌时 → 页面显示"添加品牌开始"空状态，导航标签可点击但跳转至创建页 |

#### Health 页面

```
Primary Goal: 用户看到品牌在 AI 眼中的健康状态
用户回答: "我的品牌在 AI 眼中是什么水平？"
CTA: "查看推荐方案" → 跳转到执行建议

3-second Check:
- 我在哪: "开始优化 > 品牌健康"（面包屑 + 导航高亮）
- 该做什么: 查看评分和各维度状态
- 做完得到什么: 知道品牌当前健康度，知道下一步去哪优化

Engine 降级:
- 二级标题: "Brand Health"（而非 Health Engine）
- 六维度卡片: 知识覆盖、AI 可见性、可信度、新鲜度、权威性、风险（非 Engine 术语）
- 技术概念（ADI、Health Engine、Assessment）隐藏
```

#### Discovery（扫描过程）

```
Primary Goal: 用户看到 AI 正在扫描自己的品牌
用户回答: "AI 正在了解我的品牌"
CTA: 等待扫描完成 → 自动进入 Health 页面

说明:
- 这不是一个独立的导航页面，而是 Health 页面的"扫描中"状态
- 扫描完成后自动过渡到 Health 页面（展示评分）
- 使用人类语言进度描述："正在检查官网内容结构"而非"Repository Crawl"
```

### 2.2 执行建议

| 规格 | 值 |
|---|---|
| **用户语言名称** | 执行建议 |
| **包含页面** | Recommendations 页面、Mission（优化执行） |
| **用户什么时候看到它** | 始终可见，但有推荐项时高亮（Badge 显示待执行数量） |
| **何时高亮** | 首次旅程 Phase 3（6-9 分钟），或 Health 评分<80 且有可优化项时 |
| **何时不可用/灰度** | 无品牌时 → 禁用，hover 提示"请先添加品牌"；品牌无推荐项时 → 显示"AI 还在分析中" |

#### Recommendations 页面

```
Primary Goal: 用户选择并执行品牌优化建议
用户回答: "AI 建议我做什么来提升品牌？"
CTA: "开始优化"（单个）或 "一键执行全部"（批量）

3-second Check:
- 我在哪: "执行建议 > 推荐方案"
- 该做什么: 选择一个推荐项，点击执行
- 做完得到什么: Brand Health 提升（每个卡片显示预期提升分值）

Engine 降级:
- 每个推荐卡片是"添加品牌描述"、"补充产品关键词"等人类语言
- 优先级用 红/黄/绿 + "优先级 1/2/3" 而非 Mission Level
- "由 AI 品牌引擎自动生成"仅出现在副标题（小字）
```

#### Mission（优化执行表单）

```
Primary Goal: 用户完成一项具体的优化操作
用户回答: "我在填写/编辑品牌信息"
CTA: "保存并验证" → 自动跳转到验证效果

说明:
- Mission 表单不是一个独立导航入口，而是 Recommendations 页面的二级界面
- 用户通过点击"开始优化"进入
- 使用"返回推荐列表"面包屑回溯
- 表单描述使用自然语言引导（"建议包含品牌定位、核心产品、品牌调性"）
```

### 2.3 验证效果

| 规格 | 值 |
|---|---|
| **用户语言名称** | 验证效果 |
| **包含页面** | Verification 页面 |
| **用户什么时候看到它** | 完成至少一项优化后可见；执行优化后会主动跳转到此页 |
| **何时高亮** | 首次旅程 Phase 4（9-12 分钟）；当有最新验证结果时（火焰动画 + Badge） |
| **何时不可用/灰度** | 无品牌时 → 完全禁用；有品牌但无任何优化历史 → 显示"尚无优化记录，去执行建议开始" |

#### Verification 页面

```
Primary Goal: 用户看到优化前后的品牌健康对比
用户回答: "我做的优化有效果吗？"
CTA: "返回推荐列表"（继续优化）或 "查看成长趋势"（进入持续增长）

3-second Check:
- 我在哪: "验证效果 > 优化对比"
- 该做什么: 查看 Before/After 变化
- 做完得到什么: 确认优化带来了真实提升

Engine 降级:
- 页面标题: "验证结果"（而非 Verification Engine）
- 不展示 Claim/Evidence/Verification 等概念
- 用户看到的是: "品牌描述已更新 → Brand Health +15 → 知识覆盖 32→44"

Empty State:
- 无验证历史: 显示引导"Slogan + 按钮"—— "还没有优化记录，去执行建议开始"
- 验证失败: 显示失败原因 + "重试"按钮（非静默失败，解决 Audit P1 #20）
- 加载中: Skeleton 骨架屏（解决 Audit P0 #2）
```

### 2.4 发布成果

| 规格 | 值 |
|---|---|
| **用户语言名称** | 发布成果 |
| **包含页面** | Publishing 页面、Knowledge 页面 |
| **用户什么时候看到它** | 完成至少 1 项优化后可见；首次旅程 Phase 5（12-15 分钟） |
| **何时高亮** | 所有推荐项均已执行或用户主动需要发布时 |
| **何时不可用/灰度** | 无品牌时 → 禁用；有品牌但无优化完成 → 禁用，提示"完成至少一项优化后可发布" |

#### Publishing 页面

```
Primary Goal: 用户将品牌知识发布到各个渠道
用户回答: "我的品牌信息已经发布到哪些渠道了？"
CTA: "发布到所有就绪渠道"

3-second Check:
- 我在哪: "发布成果 > 发布管理"
- 该做什么: 勾选就绪渠道 → 点击发布
- 做完得到什么: 品牌知识被分发到官网、AI 搜索引擎、社交媒体等

Engine 降级:
- 渠道名称: "官网"、"AI 搜索引擎"、"社交媒体"（非 Channel Config / Adapter）
- 状态: "已同步"、"就绪"、"需手动更新"（非 Pipeline 状态）
- 操作: "发布"（非 Trigger Delivery Pipeline）
```

#### Knowledge 页面

```
Primary Goal: 用户查看和管理品牌知识声明
用户回答: "AI 知道我品牌的哪些信息？"
CTA: "编辑知识" → 打开编辑 modal

3-second Check:
- 我在哪: "发布成果 > 品牌知识"
- 该做什么: 浏览知识声明，确认准确性
- 做完得到什么: 品牌知识被正确管理和维护

Engine 降级:
- 页面标题: "品牌知识"（而非 Knowledge Engine、Knowledge Graph）
- 声明项: "品牌名称"、"产品描述"、"联系方式"（非 Claim Statement）
- 编辑: 直接点击编辑（非 Claim Editor）

修复要点（来自 Audit P0 #1）:
- handleStatementClick 必须实现真实交互，不能仅是 console.warn
- 编辑按钮必须打开编辑界面（modal 或表单）
```

### 2.5 持续增长

| 规格 | 值 |
|---|---|
| **用户语言名称** | 持续增长 |
| **包含页面** | Dashboard 页面、Growth 页面 |
| **用户什么时候看到它** | 始终可见；首次旅程 Phase 5（12-15 分钟）高亮 |
| **何时高亮** | 主页默认入口（回归用户）；首次旅程完成第一个闭环后 |
| **何时不可用/灰度** | 无品牌时 → 禁用，hover 提示"请先添加品牌" |

#### Dashboard 页面

```
Primary Goal: 用户看到品牌全景数据和关键指标
用户回答: "我的品牌整体表现如何？"
CTA: "查看详细" → 跳转到对应页面（Health / 执行建议）

3-second Check:
- 我在哪: "持续增长 > 数据总览"
- 该做什么: 查看关键指标（品牌数量、最新评分、待办事项）
- 做完得到什么: 掌握品牌运营全局

修复要点（来自 Audit P0 #7）:
- 聚合 API 必须有 fallback，单点故障不影响其他板块
- 分块加载：Brand Health 分数、各维度卡片、趋势图分别加载
```

#### Growth 页面

```
Primary Goal: 用户看到品牌成长趋势和历史变化
用户回答: "我的品牌成长了吗？"
CTA: "继续优化" → 回到执行建议

3-second Check:
- 我在哪: "持续增长 > 成长趋势"
- 该做什么: 查看趋势图、里程碑
- 做完得到什么: 看到品牌随时间成长的轨迹

修复要点（来自 Audit P0 #5）:
- 趋势图表必须使用真实图表库（ECharts / Chart.js），不能是 CSS div 模拟
- 支持悬停、缩放等交互
- 未来趋势用虚线展示预测轨迹
```

## 3. 品牌选择器规范

### 3.1 UI 模式

品牌选择器使用**下拉模式**，置于导航栏左上角。

```
┌─────────────────────────────────────────────┐
│  🌐 云栖咖啡                        ▼  🔔 ⚙ │
│         ┌───────────────────────┐           │
│         │  当前品牌              │           │
│         │  ● 云栖咖啡   评分 60  │           │
│         │                      │           │
│         │  其他品牌              │           │
│         │  ○ 晨光茶业   评分 72  │           │
│         │  ○ 南山牧场   评分 45  │           │
│         │  ○ 漓江文创   评分 88  │           │
│         │  ─────────────────── │           │
│         │  + 添加品牌           │           │
│         └───────────────────────┘           │
└─────────────────────────────────────────────┘
```

**为什么用下拉？** Audit 显示当前 7+ 导航入口已经造成认知负担。品牌选择器应紧凑地集成到导航栏，不占用额外的侧边栏或 Tab 空间。Blueprint 的"添加品牌"操作是一个独立旅程的开始，品牌选择器应让用户在已有品牌间快速切换，而非成为日常操作的重心。

### 3.2 切换品牌时的状态保持

| 场景 | 行为 |
|---|---|
| 在同一页面切换品牌 | 当前页面保留，数据刷新为该品牌的数据。例如：在 Health 页面从"云栖咖啡"切换到"晨光茶业"，仍停留在 Health 页面，但展示晨光茶业的健康评分。 |
| 跨页面切换品牌 | 同上，保留当前路由。 |
| 当前品牌已被删除 | 自动切换到列表第一个有效品牌；如无有效品牌，跳转到创建品牌页面。 |
| 切换时数据加载中 | 显示 Skeleton 骨架屏（而非白屏或闪烁）。解决 Audit 提到的 MissionCenterShell 首次加载闪烁（P1 #13）。 |

**核心规则：切换品牌不改变当前页面路由，仅刷新数据。**

### 3.3 无品牌时的默认状态

用户没有创建任何品牌时：

- 导航栏：品牌选择器显示"未选择品牌"，无下拉项
- 所有导航项（执行建议/验证效果/发布成果/持续增长）处于**禁用状态**，hover 提示"请先添加品牌"
- "开始优化"标签可点击，跳转到品牌创建页面（Blueprint Phase 1 欢迎页）
- 页面主体：显示欢迎/引导页面 → "添加你的第一个品牌"

## 4. "我为什么来到这里？" 规范

### 4.1 面包屑/Breadcrumb 结构

面包屑为用户提供两个层次的回答：
1. **你在哪** → 导航位置
2. **你为什么在这** → 路径/来源

```
格式: [品牌] → [一级导航] → [当前页面/操作]

示例:
  云栖咖啡 → 执行建议 → 优化品牌描述
  云栖咖啡 → 验证效果 → 优化对比
  云栖咖啡 → 开始优化 → 品牌健康
```

**面包屑实现：**

```
┌───────────────────────────────────────────────────────────┐
│  🏠 云栖咖啡  >  执行建议  >  添加品牌描述                  │
│                                                           │
│  ← 返回推荐列表                                            │
│                                                           │
│  添加品牌描述                                              │
│  ┌─────────────────────────────────────────────────────┐   │
│  │  表单内容...                                         │   │
│  └─────────────────────────────────────────────────────┘   │
└───────────────────────────────────────────────────────────┘
```

**所有页面的面包屑结构：**

| 页面 | 面包屑 |
|---|---|
| Health | `品牌 → 开始优化 → 品牌健康` |
| Discovery（扫描中） | `品牌 → 开始优化 → AI 扫描中` |
| Recommendations | `品牌 → 执行建议 → 推荐方案` |
| Mission（优化表单） | `品牌 → 执行建议 → [任务名称]` |
| Verification | `品牌 → 验证效果 → 优化对比` |
| Publishing | `品牌 → 发布成果 → 发布管理` |
| Knowledge | `品牌 → 发布成果 → 品牌知识` |
| Dashboard | `品牌 → 持续增长 → 数据总览` |
| Growth | `品牌 → 持续增长 → 成长趋势` |

### 4.2 跨页面导航的语义

用户在不同页面间流动时，导航应帮助用户理解"从哪里来，到哪里去"。

| 来源 | 目标 | 导航语义 |
|---|---|---|
| Health（开始优化） | Recommendations（执行建议） | "查看推荐方案" → 用户理解：我刚才看了健康状态，现在要去优化了 |
| Recommendations（执行建议） | Verification（验证效果） | "保存并验证" → 用户理解：我执行了优化，现在去看看效果 |
| Verification（验证效果） | Recommendations（执行建议） | "返回推荐列表" → 用户理解：验证完了，回去继续优化其他项 |
| Verification（验证效果） | Growth（持续增长） | "查看成长趋势" → 用户理解：验证完了，看看品牌整体成长 |
| Growth（持续增长） | Recommendations（执行建议） | "继续优化" → 用户理解：看到成长数据，继续回去优化 |
| Publishing（发布成果） | Growth（持续增长） | "查看发布效果" → 用户理解：发布了，去看看效果 |

**关键设计：每个导航动作的 CTA 文本必须包含用户能理解的"原因"。**

例如：
- ❌ "下一步" → 用户不知道为什么下一步
- ✅ "查看推荐方案" → 用户理解：我看了健康分，现在去看看怎么提升

### 4.3 首次旅程的"导航提示"模式

新用户的前 3 次登录（或完成首个 15 分钟旅程前），导航栏显示**旅程进度提示**：

**旅程提示规范：**

| 属性 | 值 |

## 5. 下一步引导规范

### 5.1 推荐算法

每页底部或右侧显示**智能下一步推荐**。推荐逻辑基于两个维度：

1. **当前页面** — 用户在做什么
2. **当前品牌状态** — 品牌处于旅程的哪个阶段

| 当前页面 | 品牌状态 | 推荐的下一步 | 权重 |
|---|---|---|---|
| Health | 首次扫描完成，评分<60 | "查看推荐方案" 📍 | 最高 |
| Health | 评分≥60，有待优化项 | "继续优化" | 最高 |
| Health | 评分≥80 | "发布品牌知识" | 最高 |
| Recommendations | 已完成一项优化 | "验证效果" 或 "继续优化下一项" | 最高 |
| Verification | 验证完成 | "返回推荐列表" 或 "查看成长趋势" | 双选 |
| Verification | 验证失败 | "重试验证" | 最高 |
| Publishing | 发布就绪 | "发布到所有渠道" | 最高 |
| Publishing | 发布完成 | "查看成长趋势" | 最高 |
| Growth | 任何状态 | "继续优化" | 最高 |
| Knowledge | 任何状态 | "编辑知识"（有待编辑项时） | 最高 |
| Dashboard | 任何状态 | "查看健康"（未查看时） | 最高 |

**默认 fallback**：如果没有任何匹配，推荐"查看健康评分"——这是品牌运营的起点。

### 5.2 UI 模式

下一步引导使用**底部卡片**形式：

```
┌──────────────────────────────────────────────────────────┐
│                                                          │
│  （页面主体内容）                                         │
│                                                          │
│                                                          │
│  ┌────────────────────────────────────────────────────┐  │
│  │  下一步建议                                          │  │
│  │                                                    │  │
│  │  📌 建议继续优化 — 补充产品关键词（预期 +8 分）        │  │
│  │                                                    │  │
│  │  [ 去执行 → ]    [ 稍后再说 ]                       │  │
│  └────────────────────────────────────────────────────┘  │
└──────────────────────────────────────────────────────────┘
```

**UI 规范：**

| 属性 | 值 |
|---|---|
| 位置 | 页面底部（固定区域，非浮动），或右侧 Insights 面板 |
| 样式 | 浅灰背景卡片，柔和（不抢页面主体焦点） |
| 主 CTA | "[去执行 →]" 或同义操作 |
| 次要操作 | "[稍后再说]" — 点击后当天不再显示此推荐 |
| 多推荐 | 最多显示 3 项，按权重排序，取 Top 1-3 |

### 5.3 禁用/不可用状态处理

| 场景 | UI 处理 |
|---|---|
| 无品牌 | 不显示推荐（整个推荐区域隐藏） |
| 品牌扫描中 | 不显示推荐（改为显示"AI 正在分析品牌..."加载态） |
| 所有推荐已执行 | 显示"所有优化建议已执行，看看成长趋势" |
| 推荐加载失败 | 显示"暂时无法获取建议" + "刷新"按钮 |
| 当天已选择"稍后再说" | 不显示推荐 |

## 8. 迁移计划

### 8.1 迁移阶段

#### Phase A：标签改名 + 重定向（1-2 天）

**目标**：用户立即受益于任务语言导航，后端/路由不改。

| 步骤 | 操作 | 风险 |
|---|---|---|
| 1 | 左侧导航栏标签直接改名字：Health → 开始优化，Recommendations → 执行建议，Verification → 验证效果，Publishing → 发布成果，Dashboard/Growth → 持续增长 | 低风险，纯 UI 文案 |
| 2 | 添加品牌选择器下拉组件到导航栏 | 低风险，UI 组件 |
| 3 | 添加旅程进度条（首次用户） | 中风险，需 Store 记录用户状态 |
| 4 | URL 路由不改变：`/geo/health` 仍然可用 | 零风险 |
| 5 | 页面标题和面包屑改为任务语言 | 低风险 |

**效果**：用户看到的是任务语言导航，但底层路由未变。如果发现某个导航改名导致用户困惑，可快速回滚。

#### Phase B：路由重命名 + 重定向（2-3 天）

**目标**：URL 与任务语言一致，建立永久的导航架构。

| 步骤 | 操作 | 风险 |
|---|---|---|
| 1 | 添加新的路由定义（如 `/geo/start/health` 映射到 Health 组件） | 中风险（需确认前端路由框架） |
| 2 | 旧路由配置 301 重定向：`/geo/health` → `/geo/start/health` | 低风险 |
| 3 | page title 更新（`<title>` 和 meta） | 低风险 |
| 4 | 面包屑组件更新 | 低风险 |
| 5 | 外部链接/书签通知更新（可选） | 低风险 |

#### Phase C：页面体验增强（3-5 天，可与 B 并行）

**目标**：解决 Audit 发现的 P0/P1 问题，使 Navigation Architecture 的承诺可以通过真实体验验证。

| 步骤 | 操作 | 涉及 Audit |
|---|---|---|
| 1 | Health 页面修复：统一 ADI/Health 为 Brand Health | P0 #3 |
| 2 | Verification 页面：增加 Loading 骨架屏 + 空状态引导 | P0 #2 |
| 3 | Growth 页面：替换 CSS 伪图表为真实图表库 | P0 #5 |
| 4 | Knowledge 页面：实现 handleStatementClick 真实交互 | P0 #1 |
| 5 | Dashboard：API fallback 实现 | P0 #7 |
| 6 | 品牌选择器切换数据的稳定性（避免闪烁） | P1 #13 |
| 7 | 下一步推荐组件接入 | 新增 |

### 8.2 向后兼容

| 资源 | 兼容策略 |
|---|---|
| **旧 URL** | 永久保留 301 重定向。用户书签和外部链接不会失效 |
| **API 路由** | 不改。API 仍然使用 `/api/v1/geo/` 前缀，前端重新映射即可 |
| **localStorage/cookie 中存储的路径** | 重定向处理 |
| **第三方集成链接** | 建议更新，但旧链接通过 301 重定向过渡 |
| **后端** | **不需要任何改动**。Navigation Architecture 是前端层变化，所有后端服务、API 端点、数据库均不变 |

### 8.3 不需要后端改动的理由

Navigation Architecture 是**纯前端架构变化**：

1. **API 不变** — 后端仍然提供 `/api/v1/geo/health/:projectId`、`/api/v1/geo/recommendations/:projectId` 等接口
2. **数据模型不变** — DB schema、Backend Service、Engine Pipeline 不涉及
3. **权限模型不变** — 用户权限、项目隔离等不受导航变更影响
4. **路由配置变化在前端** — Vue Router / React Router 的配置修改

唯一的潜在后端影响是**旅程进度跟踪**（Phase A 第 3 步），如果需要持久化"用户是否首次使用"，则需在后端增加一个轻量字段（如 `user.first_15_min_completed`）。但这可以通过前端 localStorage + 用户注册时间实现，不是硬依赖。
