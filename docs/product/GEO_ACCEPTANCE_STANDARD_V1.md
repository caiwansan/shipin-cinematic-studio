# GEO 产品验收标准 v1.0

**依据**：《昆仑镜 GEO 产品白皮书 v1.0》第九章（Sprint 验收原则）
**状态**：冻结
**定义**：GEO 工作台每个功能的最低产品验收标准。不是测试用例，是"普通用户是否完成了业务目标"的判断基准。

---

## 验收总原则

1. **用户能完成业务目标** — 验收不是"功能跑通了"，而是"用户知道发生了什么/下一步该做什么"。
2. **商业语言优先** — 用户看到的内容不得包含 Prisma、Repository、Job Runner、State Machine、EventBus、Planner、Verification Engine 等内部架构术语。
3. **闭环完整** — 每个功能从用户操作到结果反馈的路径必须完整，不能有"显示加载完成但用户不知道结果"的情况。
4. **空态/错误态/加载态** — 三种状态都必须有用户可理解的处理。

---

## 一、品牌创建（Build）

| 验收项 | 必须达到 |
|---|---|
| 创建流程 | 用户输入品牌名称+网址，在 5 步内完成品牌创建并保存到项目列表 |
| 创建反馈 | 创建成功后项目立即出现在左侧 Projects Panel，无需刷新页面 |
| 品牌初始状态 | 新建品牌显示为"待检测"状态，而非空白或报错状态 |
| 错误处理 | 输入无效网址时给出明确提示，且不丢失已填信息 |
| 空态引导 | 无品牌时 Projects Panel 显示"创建你的第一个品牌"引导文案 |

---

## 二、AI 收录检测（Analyze）

| 验收项 | 必须达到 |
|---|---|
| 检测触发 | 用户点击"开始检测"后，系统明确反馈"检测已开始"并显示进度或预估时间 |
| 检测结果 | 检测完成后自动显示 GEO 评分，而非要求用户手动刷新 |
| 评分展示 | 总评分 + 五维评分均可见，评分含义无需额外解释 |
| 评分状态 | 正在检测中的品牌显示处理状态，而非空白或错误 |
| API 失败处理 | 检测失败时显示"检测暂时无法完成，请稍后重试"，而非报错代码 |

---

## 三、品牌质量报告（Report）

| 验收项 | 必须达到 |
|---|---|
| 报告构成 | 报告必须包含评分、问题、原因、建议四部分，缺一不可 |
| 评分含义 | 总评分附带文字说明（如"良好/需要改进/优秀"），而非仅有数字 |
| 问题列表 | 明确列出品牌当前存在的问题，每个问题附带严重度标记 |
| 原因解释 | 每个问题附带原因说明（如"官网缺少结构化数据，AI 无法准确提取产品信息"） |
| 建议输出 | 每个问题附带对应的优化建议（如"建议补充产品结构化信息"） |
| 报告保存 | 报告可保存并可追溯到生成时间 |
| 报告空白态 | 新增品牌尚未检测时，报告页面显示"请先执行 AI 收录检测" |

---

## 四、优化建议（Optimize）

| 验收项 | 必须达到 |
|---|---|
| 建议可读性 | 每条建议使用商业语言而非技术术语描述 |
| 必答问题 | 每条建议必须回答：为什么需要优化（原因）、解决什么问题（目标）、预计提升哪些指标（效果）、风险等级、优先级 |
| 建议排序 | 按重要性/权重降序排列，用户优先看到最重要的建议 |
| 建议空白态 | 无可用建议时显示"暂无优化建议，品牌状态良好" |
| 建议数量标记 | 面板显示可用建议的数量 |

---

## 五、执行优化（Execute）

| 验收项 | 必须达到 |
|---|---|
| 执行触发 | 用户点击执行后立即反馈"任务已提交"，并显示当前状态 |
| 执行进度 | 用户能实时或近实时地看到执行进度（提交→处理中→完成） |
| 执行完成 | 执行完成后自动显示结果（成功/失败/跳过及其原因） |
| 执行重试 | 执行失败后用户可一键重新执行 |
| 执行日志 | 执行完成后用户可查看简要执行日志（非技术日志，而是业务描述） |
| 执行中状态 | 执行中用户不可重复提交，按钮显示为"执行中..."并禁用 |

---

## 六、发布（Publish）

| 验收项 | 必须达到 |
|---|---|
| 发布内容可见 | 用户明确知道什么内容被发布（哪些品牌信息/FAQ/结构化内容） |
| 发布时间 | 每次发布记录精确到分钟，按时间倒排 |
| 发布状态 | 每次发布显示当前状态（待审阅/已发布/已回滚/发布中） |
| 发布对比 | 发布前后内容对比可查看 |
| 发布回滚 | 用户可回滚已发布的内容，回滚后状态清晰可见 |
| 发布空白态 | 无发布记录时显示"暂无发布记录，执行优化后即可发布" |

---

## 七、验证（Verify）

| 验收项 | 必须达到 |
|---|---|
| 验证结果可读 | 验证结果显示是否改善，而非仅显示分数变化 |
| 验证回朔 | 每次验证可追溯到对应的优化执行 |
| 验证对比 | 用户可选择两次验证记录进行前后对比 |
| 验证空白态 | 无验证记录时显示"暂无验证记录，执行优化后自动验证" |

---

## 八、持续监测（Monitor）

| 验收项 | 必须达到 |
|---|---|
| 告警可见 | 有告警时用户能在面板顶部的醒目位置看到告警标记 |
| 告警详情 | 点击告警标记后可查看告警列表，每条包含类型/严重度/发生时间 |
| 趋势可见 | 用户能看到品牌评分在时间上的变化趋势 |
| 漂移告警 | 品牌一致性下降时系统主动提示 |
| 监测空白态 | 无可告警时显示"品牌状态正常" |

---

## 九、全局 UX 验收

| 验收项 | 必须达到 |
|---|---|
| 加载状态 | 每个面板在数据加载时显示骨架屏或加载指示器 |
| 错误状态 | API 调用失败时所有 Tab 显示友好的错误提示，不影响其他 Tab |
| 空状态 | 每个列表类组件（项目列表/建议列表/发布列表/验证列表）在无数据时显示引导文案 |
| 操作反馈 | 所有按钮点击后 500ms 内必须给出操作反馈（状态变化/loading/Toast） |
| 状态一致性 | 执行中的任务在 InsightsPanel 和 Evidence Tab 中状态一致 |

---

## 十、验收流程

```
Sprint 完成
     │
     ▼
开发者自验（对照此标准逐项检查）
     │
     ▼
产品验收（你或代表逐项确认）
     │
     ▼
全通过 → 合入主线
     │
     未通过
     │
     ▼
返回修改 → 重新验收
```

*Sprint 提交验收时，必须附带一份"验收对照表"说明每项是否符合标准。不符合项需说明原因和预计修复时间。*
