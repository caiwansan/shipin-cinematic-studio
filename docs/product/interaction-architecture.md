# GEO Interaction Architecture

> **定义所有页面统一的 AI 交互节奏 —— 用户在不同页面感受到同一套产品语言**
>
> 版本：v1.0
> 依据：First 15 Minutes Blueprint v1.0 · Navigation Architecture v1.0 · Product Readiness Audit
> 冻结日期：2026-07-26

---

## 为什么需要 Interaction Architecture

Audit 显示产品处于 **Power User Ready** 状态（Cognitive Load 评估 3/5），但新用户在不同页面间感受到的不是同一套产品语言：

- DiscoveryLabPage 有 Loading 骨架屏，VerificationPage 完全空白
- MissionCard 的 Explain 展开方式与 Dashboard 的 Activity Explain 不同
- 有些页面在 AI 工作时有进度指示，有些没有
- 失败反馈的呈现方式不统一

Navigation Architecture 解决了"我在哪"和"我去哪"的问题，但没有定义"交互过程是怎样的"。Interaction Architecture 补上这一层——定义所有 AI 交互共用一套节奏，让用户在任何页面都感受到同一套产品语言。

**核心原则：所有 AI 交互遵循同一个 7 步节奏。不因页面不同而改变交互协议。**

---

## 1. 核心交互模型（The GEO Interaction Rhythm）

所有 AI 交互遵循以下 7 步节奏：

```
用户触发动作
    ↓  (Step 1)
即时反馈（200ms 内）
    ↓  (Step 2)
AI 工作状态（如果耗时 > 1s）
    ↓  (Step 3)
Explain（发生了什么 + 为什么）
    ↓  (Step 4)
Action（用户可以操作什么）
    ↓  (Step 5)
Feedback（成功了还是失败了）
    ↓  (Step 6)
Next Step（下一步去哪）
    ↓  (Step 7)
返回 idle 或进入下一个循环
```

**为什么是 7 步？** 因为需要覆盖用户从"我想做某事"到"我知道结果并知道接下来做什么"的完整心理弧线。步数太少则丢失关键体验（如 Explain），太多则造成不必要的认知负担。7 步是 Goldilocks 数字——Blueprint 定义的三秒原则要求在每一步都回答"我在做什么、做完得到什么、下一步去哪"。

### Step 1: Trigger（用户触发）

用户通过以下方式触发 AI 操作：

| 触发方式 | 说明 | 示例 |
|---------|------|------|
| 按钮点击 | 用户点击明确的 CTA | "开始检测"、"保存并验证"、"发布" |
| 表单提交 | 用户填写信息后提交 | 创建品牌表单、"一键执行全部" |
| 导航进入 | 用户进入某个页面触发 | 进入 Recommendations 页面触发重新分析 |
| 自动触发 | 系统在特定条件自动发起 | 品牌创建后自动触发扫描 |

**前置条件检查（在触发前执行）：**

触发前系统必须检查以下条件，任一不满足则阻止触发并给出明确提示：

| 检查项 | 失败时提示 | 适用场景 |
|--------|-----------|---------|
| 数据就绪 | "数据尚未加载完成，请稍后重试" | 所有操作 |
| 权限到位 | "你没有执行此操作的权限" | 发布/删除等敏感操作 |
| 不是 loading 状态 | 不需要提示，按钮已禁用 | 所有操作 |
| 没有 pending 操作 | 一个操作完成前不触发新操作 | 所有操作 |
| 输入完整性 | 表单验证提示 | 表单提交 |

**防重复触发机制：**

| 机制 | 实现方式 | 适用场景 |
|------|---------|---------|
| 按钮禁用 | 触发后立即 disable 按钮，文案切换为 loading | 所有按钮操作 |
| Debounce | 300ms 内不重复触发 | 自动触发场景 |
| 请求锁 | Store 中维护 `isPending` 状态，阻止并发请求 | 所有异步操作 |

**为什么需要版本触发检查？** 当前 MissionCard `handleExecute` 绕过 service 层直接 fetch（Audit P1 #11），`useWorkflowStore.goNext` 失败时无 UI 反馈（Audit P1 #15）。这些问题的根因是触发层没有统一的前置检查机制。

### Step 2: Instant Feedback（即时反馈，<200ms）

用户触发操作后，系统必须在 **200ms 内** 给出视觉确认。这是 Nielsen 响应时间的硬性阈值——超过 200ms 用户会感觉"卡"。

**反馈矩阵：**

| 触发类型 | 即时反馈 | 说明 |
|---------|---------|------|
| 按钮点击 | 按钮切换为 loading 态（spinner + 文案变化） | 最常见反馈方式 |
| 表单提交 | 提交按钮 loading + 表单字段锁定 | 防止用户继续编辑正在提交的字段 |
| 导航进入 | 页面切换动画 + Skeleton 骨架屏 | 让用户知道"已开始加载" |
| 自动触发 | 进度条显示或状态变更提示 | 如扫描开始 |

**按钮状态变化规范：**

```
默认态: [ 开始优化 → ]
触发后: [ ◌ 提交中... ]    ← 200ms 内切换
                                 按钮变为 disabled
                                 颜色从 primary 变为 muted-primary
```

**文案变化规范：**

| 默认文案 | Loading 文案 | 规范 |
|---------|-------------|------|
| 开始优化 | 优化中... | 动词变为进行时 |
| 保存并验证 | 正在验证... | 明确"在做什么" |
| 发布 | 发布中... | 简洁 |
| 开始检测 | 检测中... | 简洁 |
| 一键执行全部 | 正在执行... | 同上 |

**预测性展示（可选增强）：**

如果 AI 操作有可预测的结果形式，可以在触发后立即展示结果的"骨架预览"。例如：

- 扫描任务：展示 Health 页面的**骨架版**——6 个维度卡片的灰色占位，告诉用户"结果将在这里展示"
- 验证任务：展示 Before/After 对比区域的**骨架版**

预测性展示不是必须的，但能显著降低用户在等待期的不确定性。优先在以下场景使用：
- 首次创建品牌后的扫描（Phase 2）
- 优化后的验证过程（Phase 4）

---

### Step 3: AI Working State（AI 工作状态，>1s 时展示）

如果 AI 操作耗时超过 1s，展示明确的工作状态。1s 是用户对"即时操作"的心理预期阈值——超过 1s 用户会开始怀疑系统是否卡住。

**进度指示器选择：**

| 场景 | 进度类型 | 组件 | 说明 |
|------|---------|------|------|
| 耗时 1-5s，有确定进度 | 确定进度 | 线性进度条（带百分比） | 扫描过程（当前 Blueprint 已有） |
| 耗时 >5s，有阶段划分 | 分阶段进度 | 步骤指示器 + 当前步骤名称 | 批量执行多个 Mission |
| 耗时不确定 | 不确定进度 | 循环加载动画 + 状态文案 | API 调用时间不可预测时 |
| 耗时 >30s | 后台处理 + 通知 | 进度条 + "完成后通知你" | 发布后等待 AI 渠道同步 |

**状态文案规范：**

| ❌ 技术语言 | ✅ 用户语言 |
|-----------|-----------|
| "Loading..." | "AI 正在分析你的品牌..." |
| "Processing..." | "AI 正在验证优化效果..." |
| "Fetching data..." | "正在加载品牌数据..." |
| "Executing pipeline..." | "正在执行优化建议..." |

**分阶段展示规范：**

如果 AI 操作有明确的多阶段过程，必须分阶段展示。每个阶段显示：

```
当前总进度: ████████░░░░░░  65%    ← 总体进度
正在检查: 官网内容结构           ← 当前阶段名称（人类语言）
已完成: 品牌基本信息 ✓           ← 已完成阶段（绿色 + 勾选）
待完成: AI 推荐结果             ← 待完成阶段（灰色）
        外部渠道覆盖
```

分阶段展示的适用场景：
- 首次品牌扫描（3-5 阶段）
- 批量执行多个 Mission
- 发布到多渠道

**取消操作规范：**

| 场景 | 是否可取消 | UI 反馈 |
|------|-----------|---------|
| 扫描过程 | ✅ 可取消 | 进度条旁显示"取消扫描"按钮 |
| Mission 执行 | ✅ 可取消 | 弹出确认对话框"确定取消？已执行的更改不会丢失" |
| 验证过程 | ❌ 不可取消 | 不提供取消按钮（验证是只读操作，无副作用） |
| 发布过程 | ✅ 可取消 | 仅取消"待发布"的项，已发布的不可撤回 |
| 重新分析 | ❌ 不可取消 | 不提供取消按钮 |

取消后的状态过渡：`ai_working → cancelled → idle`

**超时处理规范：**

| 超时阈值 | 行为 |
|---------|------|
| > 预期时间 30s | 展示提示："AI 处理时间超出预期，请稍候..." |
| > 预期时间 60s | 展示提示 + "重试"按钮 |
| > 预期时间 120s | 自动终止 + 展示失败状态 + "系统超时，请重试" |

**为什么需要超时处理？** 当前 `missionControlService` 无请求超时机制（Audit P1 #17）。如果后端卡住，前端会无限等待。超时处理是交互架构的兜底机制。

### Step 4: Explain（发生了什么 + 为什么）

AI 输出后的第一屏展示必须回答两个问题：

1. **发生了什么** — AI 做了什么（Summary）
2. **为什么** — AI 为什么这么做（Explain）

**第一屏展示规范：**

Always show → First Screen: Summary
```
Brand Health: 45 → 60  (+15)
```
AI 做了什么 + 核心变化

Available on click → Second Screen: Explain Drawer
```
为什么提升了 15 分？
- 品牌描述已补充 → 知识覆盖 +12
- 关键词已优化 → AI 可见性 +3
```
AI 为什么这么做 + 详细原因

**与 ExplainDocument 的映射关系：**

ExplainDocument 是 Explain 层的数据模型（评分 9/10，是当前代码中质量最高的模块）。Interaction Architecture 直接使用它的字段：

| ExplainDocument 字段 | 在 Rhythm 中的用法 | 展示位置 |
|---------------------|-------------------|---------|
| `summary` | Step 4 的第一屏 — 发生了什么 | 页面主体，Always show |
| `explanation` | Step 4 的第二屏 — 为什么 | Explain Drawer，点击展开 |
| `evidence` | 支撑"为什么"的证据来源 | Explain Drawer 内部 |
| `confidence` | 可选—AI 对结果的置信度 | 小字标注在分数旁 |
| `impact` | Step 5 的输入—"可以做什么" | Action 区域的建议文案 |
| `nextSteps` | Step 7 的输入—"下一步去哪" | Next Step 区域的推荐 |

**关键约束：Never overload the first screen.**

第一屏只展示 `summary`。`explanation`、`evidence`、`confidence` 等详情在 Explain Drawer 中展示。这是 Progressive Disclosure（P7）原则。

**Explain Drawer 打开/关闭规范：**

| 操作 | 行为 | 动画 |
|-----|------|------|
| 点击"了解为什么" | 从右侧滑出 Drawer | 200ms ease-in-out |
| 点击关闭 / 遮罩层点击 | 收起 Drawer | 200ms ease-in-out |
| 点击 Drawer 内 CTA | 关闭 Drawer + 执行操作 | 同上 |

> 当前 GeoExplainDrawer 宽度固定，无响应式（Audit 评分 8/10）。Interaction Architecture 要求 Drawer 宽度为 `min(540px, 90vw)`。

**为什么第一步展示 summary 而非 explain？** 因为用户的第一需求是"告诉我结果是什么"，而不是"告诉我为什么"。Audit 中 Cognitive Load 评估显示，用户最大的痛点是信息过载而非信息不足。先展示结果，再提供深入入口。

### Step 5: Action（用户可以做什么）

AI 输出后，用户需要有明确的行动路径。

**行动层级：**

| 层级 | 定义 | 按钮样式 | 数量限制 |
|-----|------|---------|---------|
| 主要操作 | 最推荐用户做的操作 | Primary 样式 | 1 个 |
| 次要操作 | 可选的补充操作 | Outline 样式 | 1-2 个 |
| 链路操作 | 离开当前流程的其他路径 | Text/ghost 样式 | 不限 |

**常见行动组合：**

| 场景 | 主要操作 | 次要操作 | 链路操作 |
|------|---------|---------|---------|
| 扫描完成 | "查看推荐方案" | "重新扫描" | "了解 Brand Health" |
| 优化完成 | "保存并验证" | "查看详情" | "取消" |
| 验证完成 | "返回推荐列表" | "查看成长趋势" | "查看完整报告" |
| 发布完成 | "查看发布效果" | "继续优化" | "管理渠道" |
| 操作失败 | "重试" | "查看原因" | "返回" |

**AI 建议的行动 vs 用户自主的行动：**

| 类别 | 定义 | 展示方式 |
|-----|------|---------|
| AI 建议 | AI 根据分析结果推荐的操作 | 主要操作按钮（Primary） |
| 用户自主 | 用户自己决定的其他操作 | 次要/链路操作按钮 |

AI 建议不能是唯一的操作路径。必须保留用户自主选择的权利（Trust Before Automation 原则）。

### Step 6: Feedback（成功/失败）

Feedback 是用户信心的来源。不一致的反馈是当前产品最大的体验断裂点。

**成功反馈规范：**

| 组件 | 规范 |
|------|------|
| 颜色 | 绿色（Brand OS Design System success color） |
| 图标 | ✓ 或 🎉（视成功程度） |
| 字数 | ≤ 15 字 |
| 数字变化 | 必须展示具体变化值（如 "+15"） |
| 文案结构 | `[动作完成] + [具体变化] + [影响]` |

示例：
```
✓ 品牌描述已更新，Brand Health +15 分
🎉 3 项优化全部完成，预计总分提升 +28 分
✓ 品牌知识已发布到 2 个渠道
```

**失败反馈规范：**

| 组件 | 规范 |
|------|------|
| 颜色 | 红色（Brand OS Design System error color） |
| 图标 | ✗ 或 ⚠️（视失败严重程度） |
| 文案结构 | `[失败原因] + [可操作的重试建议]` |
| 必须包含 | 原因（用户语言） + 重试按钮 |

示例：
```
✗ AI 暂时无法验证品牌描述
原因：官网暂时无法访问
[ 重试 ]  [ 稍后再说 ]
```

```
✗ 发布到 AI 搜索引擎失败
原因：品牌信息验证未通过，缺少联系方式
[ 补充信息 ]  [ 稍后重试 ]
```

**部分成功规范：**

AI 操作中可能出现部分成功部分失败的情况（如批量执行 3 个 Mission，2 个成功 1 个失败）。

| 组件 | 规范 |
|------|------|
| 颜色 | 黄色（Brand OS Design System warning color） |
| 图标 | ⚠️ |
| 文案结构 | `[成功数]/[总数] 操作成功，[失败数] 项需处理` |

示例：
```
⚠️ 2/3 项优化已执行成功
   ✓ 添加品牌描述 — 已完成
   ✓ 补充产品关键词 — 已完成
   ✗ 提交品牌 Logo — 需补充图片文件
[ 补充 Logo ]  [ 查看结果 ]
```

**反馈持续时间规范：**

| 反馈类型 | 展示方式 | 持续时间 | 关闭方式 |
|---------|---------|---------|---------|
| 成功 | Inline（页面内嵌） | 持续可见（结果态） | 用户离开页面 |
| 成功（辅助） | Toast | 3s 自动消失 | 自动 |
| 失败 | Inline（页面内嵌） | 持续可见 | 用户手动处理 |
| 失败（辅助） | Toast | 持续可见 | 用户手动关闭 |
| 部分成功 | Inline（页面内嵌） | 持续可见 | 用户手动处理 |

**为什么会持续可见？** 成功反馈是"结果"的一部分——用户回来查看应该能看到。只有辅助性的 Toast 提示才自动消失。Blueprint 的"三秒原则"要求用户在进入页面时知道"发生了什么"，成功反馈应该像看板一样保持可见。

**当前现状：** MissionCard 执行后只在按钮上显示短暂状态，没有持久化的成功/失败标记。VerificationPage 失败后没有可操作的重试按钮（Audit P1 #20）。这些都违反了 Interaction Architecture 的规范。

---

### Step 7: Next Step（下一步去哪）

用户完成一个操作后必须知道"接下来该做什么"。这是 Blueprint 三秒原则中"做完得到什么"的延伸。

**推荐逻辑：**

| 当前操作结果 | 推荐的下一步 | 优先级 |
|-------------|------------|-------|
| 扫描完成（首次） | "查看推荐方案" → Recommendations | 最高 |
| 扫描完成（非首次） | "查看详细评分" → Health | 最高 |
| 优化执行完成 | "验证效果" → Verification | 最高 |
| 验证完成（有剩余推荐） | "继续优化下一项" → Recommendations | 最高 |
| 验证完成（全部完成） | "查看成长趋势" → Growth | 最高 |
| 发布完成 | "查看发布效果" → Growth/Verification | 最高 |
| 操作失败 | "重试该操作" | 最高 |
| 任何状态（无更优推荐） | "查看品牌健康" → Health | Fallback |

**UI 规范：**

```
┌──────────────────────────────────────────────────────────┐
│  下一步建议                                                │
│                                                          │
│  📌 建议继续优化 — 补充产品关键词（预期 +8 分）              │
│                                                          │
│  [ 去执行 → ]    [ 稍后再说 ]                             │
└──────────────────────────────────────────────────────────┘
```

"稍后再说"规则：点击后，当天不再显示该特定推荐项。

仅在下列情况不显示 Next Step：
- 状态为 `loading` 或 `ai_working`（用户正在等待）
- 无品牌（用户尚未创建品牌）

**关闭/完成状态：**

如果用户已完成旅程中的所有可用操作（所有推荐已执行、已验证、已发布），Next Step 区域展示：

```
🎉 所有优化建议已执行！品牌健康度已达到最佳状态
[ 查看成长趋势 ]  [ 添加新品牌 ]
```

## 2. 状态系统（The GEO State System）

所有 AI 交互共用一套状态枚举。这是 Interaction Architecture 实现的核心。

### 2.1 状态枚举

```
idle           → 就绪，等待用户操作
loading        → 用户已触发，系统工作中（<1s 预期）
ai_working     → AI 正在处理（>1s 且需要进度展示）
success        → 操作成功
failure        → 操作失败
partial        → 部分成功（操作完成但部分子项失败）
timeout        → 超过预期时间
cancelled      → 用户取消操作
```

### 2.2 状态转换图

```
                   ┌─────────────────┐
                   │      idle       │
                   └────────┬────────┘
                            │ 用户触发
                            ↓
                   ┌─────────────────┐
              ┌────│    loading      │────┐
              │    └────────┬────────┘    │
              │             │ >1s         │ <1s
              │             ↓             │
              │    ┌─────────────────┐    │
              │    │   ai_working    │    │
              │    └────────┬────────┘    │
              │             │ 完成        │
              │             ↓             │
              │    ┌─────────────────┐    │
              │    │   completed     │    │
              │    └───┬───┬───┬────┘    │
              │        │   │   │         │
              │        ↓   ↓   ↓         │
              │    success partial failure│
              │        │   │   │         │
              │        └───┴───┘         │
              │             │            │
              │             ↓            │
              │    ┌─────────────────┐   │
              │    │    timeout      │   │
              │    └─────────────────┘   │
              │                          │
              │   cancel ←───────────────┘
              │     ↓
              └──── cancelled
                        │
                        ↓
                     idle (返回初始)
```

**关键约束：**

- `loading` 和 `ai_working` 是互斥的——系统要么在快速加载（loading），要么在长时间工作（ai_working）
- `loading` → `ai_working` 是单向的：一旦进入 `ai_working`，即使进度恢复到 <1s，也不回退到 `loading`
- `timeout` 是 `ai_working` 的特殊子状态（超过预期时间）
- `cancelled` 只能从 `loading` 或 `ai_working` 进入
- `success`、`failure`、`partial` 是终态，再次触发后重置为 `loading`

### 2.3 每个状态的 UI 规范

| 状态 | 颜色 | 文案风格 | 动画 | 持续时间 |
|------|------|---------|------|---------|
| idle | 品牌色（默认 blue-500） | 引导性文案："开始优化你的品牌吧" | 无 | 无限（用户触发前） |
| loading | 品牌色（muted-blue） | 动词进行时："验证中..." | 按钮 spinner（旋转，周期 1s） | <1s 或直到完成 |
| ai_working | 品牌色 + 进度条蓝 | 正在进行 + 阶段描述："AI 正在分析品牌描述..." | 进度条动画（线性增长）或循环光晕 | 直到完成/取消/超时 |
| success | 绿色（green-500） | 结果性文案 + 数字变化："✓ 品牌描述已更新 +15 分" | 轻微的弹出或放大（scale 1.0→1.02, 200ms） | 持续可见（页面级） |
| failure | 红色（red-500） | 原因 + 可操作建议："✗ 验证失败，官网暂时无法访问" | 抖动动画（shake, 300ms） | 持续可见直到用户处理 |
| partial | 黄色（yellow-500） | 成功数/总数 + 待处理项："⚠️ 2/3 项成功" | 轻微闪烁（fade, 500ms） | 持续可见直到用户处理 |
| timeout | 红色（red-400） | 超时提示 + 重试建议："系统超时，请重试" | 渐入（fade in, 300ms） | 持续可见直到用户重试 |
| cancelled | 灰色（gray-400） | 确认文案："已取消" | 渐变消失（fade out, 300ms） | 3s 后自动消失或立即返回 idle |

### 2.4 状态在代码中的使用方式

每个 AI 交互组件应维护一个状态属性：

```typescript
// 伪代码 — 状态类型定义
type InteractionState = 
  | 'idle'
  | 'loading' 
  | 'ai_working'
  | 'success'
  | 'failure'
  | 'partial'
  | 'timeout'
  | 'cancelled';

interface InteractionStateMachine {
  current: InteractionState;
  progress?: number;      // 0-100, 仅 ai_working 时有效
  phase?: string;         // 当前阶段名称, 仅 ai_working 时有效
  phases?: Phase[];       // 所有阶段列表, 仅 ai_working 时有效
  message?: string;       // 状态描述文案
  error?: ErrorDetail;    // 错误详情, 仅 failure/timeout 时有效
}
```

**为什么需要统一的状态系统？** 当前代码中没有统一的状态管理——MissionCard 有独立的 loading 状态，VerificationPage 完全没有状态管理，RecommendationsPage 的状态由父组件传递。这导致每个页面的交互行为不一致。统一的状态系统让所有组件共享同一套交互协议。

### 3.1 页面映射表

| **Health**（非首次） | 页面加载 | `idle → loading → success` 或 `idle`（缓存命中） | 快速加载，骨架屏过渡；无 AI 操作等待 |
| **Recommendations** | 页面加载 / 点击"重新分析" | `idle → loading → success` 或 `idle → empty` | 无 AI 操作时直接展示缓存结果；重新分析时展示扫秒进度 |

| **MissionCard（Explain）** | 点击"了解为什么" | `idle → loading → success`（展示 Explain Drawer） | 纯读取，无写操作；Drawer 打开后进入 idle |
| **Verification** | 优化完成时自动跳转 | `idle → loading → ai_working → success/failure → next_step` | Before/After 对比；无验证历史时展示引导状态（非空白） |
| **Verification**（手动进入） | 点击"验证效果"导航 | `idle → loading → success` 或 `idle → empty` | 无最新验证结果时展示"尚无优化记录" |
| **Publishing** | 点击"发布" | `idle → loading → success/failure → next_step` | 发布后展示预期同步时间；重试逻辑完整 |
| **Publishing**（页面加载） | 页面加载 | `idle → loading → success` 或 `idle` | 数据聚合展示，无单个 AI 操作 |
| **Dashboard/Growth** | 页面加载 | `idle → loading → success` 或 `idle`（缓存命中） | 聚合数据，无单个 AI 操作。分块加载各数据模块 |
| **Knowledge** | 页面加载 / 点击编辑 | `idle → loading → success` 或 `idle` | 编辑操作独立交互；声明交互非 stub（需修复 Audit P0 #1) |

## 4. 错误处理协议

统一的错误处理策略，确保错误反馈在所有页面一致。

### 4.1 错误分类

| 错误类型 | 定义 | 识别方式 | 示例 |
|---------|------|---------|------|
| **客户端错误** | 前端输入验证失败 | 前端校验 | 必填字段为空、格式错误 |
| **网络错误** | 请求无法到达后端 | `fetch`/`axios` 网络异常 | 断网、DNS 解析失败 |
| **AI 错误** | AI 服务返回错误 | 后端返回特定 error code | AI 无法分析、模型超时 |
| **超时** | 请求超过预期时间 | `AbortController` / 时间检测 | >30s 无响应 |
| **权限不足** | 用户无操作权限 | 后端返回 403 | 非品牌所有者尝试发布 |
| **服务端错误** | 后端服务异常 | 后端返回 5xx | 服务崩溃、数据库异常 |

### 4.2 错误展示层级

| 错误类型 | 展示方式 | 位置 | 严重程度 |
|---------|---------|------|---------|
| 客户端错误 | Inline | 表单字段下方 | 低（用户可修正） |
| 网络错误 | Toast（全局） | 页面右上角 | 中（网络问题） |
| AI 错误 | Inline（页面级） | 操作区域 | 高（AI 不可用） |
| 超时 | Inline（页面级） | 操作区域 | 高（需用户决定） |
| 权限不足 | Toast（全局） | 页面右上角 | 中（非技术问题） |
| 服务端错误 | 页面级（或 Toast） | 页面主体或右上角 | 高（系统问题） |

**错误展示方式详解：**

**Inline（内联）** — 在触发点附近直接展示错误信息。适用于用户可自行修正的错误。

```
┌──────────────────────────────────────────────┐
│  品牌描述：                                    │
│  ┌────────────────────────────────────────┐   │
│  │                                    ✗   │   │
│  └────────────────────────────────────────┘   │
│  品牌描述不能超过 500 字                        │
└──────────────────────────────────────────────┘
```

**Toast（全局）** — 在页面右上角展示，不打断用户当前操作。适用于非阻塞性错误。

```
┌──────────────────────────────────────────────┐
│  ✗ 网络连接已断开，请检查网络     [ 重试 ]  ✕  │
└──────────────────────────────────────────────┘
```

**页面级（Error Page/Block）** — 替换页面主要内容区域。适用于破坏性的错误（AI 不可用、服务宕机）。

```
┌──────────────────────────────────────────────┐
│                                              │
│            ⚠️ AI 服务暂时不可用                 │
│                                              │
│  正在尝试自动恢复...                            │
│                                              │
│  [ 手动重试 ]  [ 稍后再说 ]                   │
│                                              │
└──────────────────────────────────────────────┘
```

### 4.3 重试策略

| 错误类型 | 策略 | 行为 |
|---------|------|------|
| 客户端错误 | 手动重试 | 用户修正输入后重新提交 |
| 网络错误 | 自动重试（1次）→ 手动重试 | 自动重试 1 次，失败后展示"重试"按钮 |
| AI 错误 | 手动重试 | 展示"重试"按钮，提供降级建议 |
| 超时 | 手动重试 | 展示"重试"按钮，或建议稍后操作 |
| 权限不足 | 不重试 | 引导用户联系管理员或切换账号 |
| 服务端错误 | 自动重试（1次）→ 手动重试 | 同网络错误 |

**自动重试规范：**

- 自动重试仅限一次（避免无限死循环）
- 自动重试时不展示新的 Toast，保持原有 loading 状态
- 自动重试间隔：3s
- 自动重试失败后，展示手动重试界面

**降级建议：**

当 AI 错误持续发生时，应提供降级方案而非让用户无限点击重试：

| AI 操作 | 降级建议 |
|---------|---------|
| 品牌扫描 | "AI 暂时无法分析，请稍后再试。你也可以手动填写品牌信息。" |
| Mission 执行 | "AI 优化暂时不可用，建议你手动更新官网内容后重新检测。" |
| 验证 | "AI 验证暂时不可用，建议稍后重试。" |
| 发布 | "发布暂时不可用，你可以在官网自行更新信息。" |

| "Error: 503 Service Unavailable" | "AI 服务暂时繁忙，请稍
